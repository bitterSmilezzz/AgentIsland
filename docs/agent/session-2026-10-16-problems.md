## 8. 专项：清理自造探测数据时误删真实数据（C-15）

**做了什么**：为端到端验证事件类型覆盖，我向**真实常驻应用**投递探测事件，之后清理。

**造成的事故**：第二次清理用「时间戳 ≥ 02:10」当判据，比实际污染范围**更宽**，
一次删掉 21 条，其中包含**用户真实事件**；更早的投递还触发 `pending` 上限 64，
**静默挤掉最早的真实条目**。事后从 `/tmp` 备份恢复为 55 条真实事件（00:00→23:46）。

**为什么会错**：

1. **把「我产生的那批」误当成「那个时间段」**。正确判据是从投递前备份里 diff 出的**精确 id 集合**；
   时间窗口会随我后续投递不断变宽。
2. **忽略有界容量的连带淘汰**：`pending` 上限 64，任何多余投递都会挤掉一条最早的真实记录。
   「只投一条自造数据」在这个账本上**并不无害**。
3. **在用户真实运行的应用上做写操作**。本仓库已有隔离实例
   （`--background-test`/`--ui-smoke` 走独立 bundle id、不启用账本持久化），我却选了污染真实状态那条路。
4. **备份粒度不足**：只有 02:06 与 02:09 两份，两者之间的真实事件只能靠并集尽力恢复，
   无法逐字节证明完整。

**硬规则（建议升级为规范）**：

- **禁止向用户常驻应用投递探测事件**；验证走隔离实例或临时 fixture 探针。真实账本只读。
- 确需写真实状态时：**先停应用 → 复制整份账本 → 只按 id 集合删 → 重启 → 逐条 diff 复验**。
- 注意容量连带淘汰：注入 N 条会挤掉最多 N 条真实记录；容量满时尤其不可注入。
- 清理的**目标状态**是「与投递前逐条一致」，不是「看起来干净了」。

**当前状态的诚实口径**：账本现有 55 条真实事件，比原始 64 条少 9 条；
差额是首次污染挤掉的、且备份里也不存在的条目，**无法恢复也无法证明是哪几条**。
这是我的操作造成的，不是产品缺陷。

### 构建锁的最终边界

原有 `artifact.py` 有两层机制：`.artifact-lock` 是状态变更短锁；`active` 从begin保持到finish/fail，已经能拒绝另一轮正常begin。初稿“保护只到收据生成，编译阶段完全无保护”错误。

不能全程占用 `.artifact-lock`：finish/fail需再次获取，verify也会拒绝，结果是自我拒绝。新增独立稳定文件 `.build/heavy-build.lock`，Python `fcntl.flock(LOCK_EX|LOCK_NB)` 后设置fd可继承并exec构建链。无需外部flock命令，不删除锁文件、不按PID猜测陈旧锁。

- 同一仓库经锁入口启动的命令互斥；忙碌返回2且不进入artifact begin。
- 内核锁保持到最后一个继承描述符关闭；不覆盖调用方EXIT trap。
- artifact的active/failed状态独立保留。内核锁释放不会清除中断现场或自动给旧包签新收据。
- 已接入 `build-app.sh`；任意直接cargo及Windows脚本不自动受它约束。锁不限制单任务CPU，也不阻止顺序重复构建。
- 锁库和Python helper列入产物源码摘要；测试沙箱复制真实依赖，修改helper也会改变摘要。
