# v0.0.196 独立复核 · DSH · 2026-09-27 20:20

## 范围与结论

按 [ADR 0013](../adr/0013-local-event-port-during-migration.md) 把两个应用的本地入口端口分开，
并修掉一处跨实现互操作缺口。结论：两个应用可同时运行、各自答话；同一份「Swift 格式」的请求
两边都接受。Swift 侧零业务改动。

## 决定与依据

`41999` 是 README 对第三方的承诺（`SelfReport.defaultPort`，Core 里唯一定义处），
指向它就该指向**今天真正交付的应用** ⇒ 交付物保持 41999，Rust 端用 42000
（可 `AGENTISLAND_EVENT_PORT` 覆盖、`0` 让内核挑、认不出回落默认而不是 panic）。
Swift 退场时改回 41999。两侧都把端口与绑定失败写进日志——原先 Rust 是**静默退化**。

## 可核验的证据

- **并存实测**：Swift 占着 41999 时启动 Rust 端 ⇒ 日志 `监听 127.0.0.1:42000`（无失败行）；
  `lsof` 两个端口各有一个监听者（42000=agentisla / 41999=AgentIsla）；
  42000 回 `{"bound":true,"expiresAt":1790511514}`，41999 仍正常答话。
- **互操作实测**：同一份「Swift 格式」请求（`?agent=dim` + 正文 `session`）两边都回
  `{"bound":true,"expiresAt":…}`——Rust `1790511695`（整数秒）、Swift `1790511695.9989`（小数秒）。
- **测试** Rust 295 → **299**；编译警告保持 **17**。
- **纯函数缝**：`parse_event_port` 与 `resolve_session_ids` 都不依赖环境变量即可测
  （`std::env::set_var` 是进程级共享状态，拿它测等于埋偶发）。

## 本轮真正值得记的一条

那处互操作缺口（Swift 的 `session` 在正文里、我两个都从查询串取）**不是测试发现的，是对打发现的**：
我拿真跑的 Swift 应用发同一份请求，它回「缺 session」——而我的实现按自己的理解写、自己的测试
也按自己的理解写，两边一致但都错了。**「两份实现互相验证」比「自己测自己」强的地方就在这里。**
（顺带：这也是我上一轮被端口抢占骗过之后的第二个「只有对打才暴露」的问题。）

## 边界与后续风险

- **第三方同时喂两个应用**没有真实样本（要装 hook 才能验）；今天只验到「各自答话、互不打扰」。
- `expiresAt` 整数/小数之差今天两边都能被 JSON 消费方接受，未统一。
- Rust 的撤销响应形状仍未与 Swift 逐字核对（`{revoked:bool}`）。
- 端口可配置带来一个新的失败方式：环境变量写错会落到默认端口，
  表现为「第三方配的端口没人听」——日志里有实际端口，可查。
- 同前几轮：同一人既改又审；护栏是两处反向验证 + **对打**（而这次对打是本轮唯一的发现渠道）。
