# v0.0.173 独立复核 · DSH · 2026-09-27 06:23

## 范围与结论

复核上一轮记录的真实缺陷修复：`push_event` 覆盖式赋值导致同拍告警丢一条。
改为「队首上屏 + 待发队列 + 逐条确认」，并把 refresh 里的接线抽成可测函数。
结论：**缺陷已修、有判别性用例、反向验证成立**；形态与 Swift 的事件流仍不同（已记录）。
Swift 侧零改动。

## 缺陷与修法

```rust
// 修前：后一条无条件顶掉前一条
pub fn push_event(&mut self, event: AgentTaskEvent) { self.latest_event = Some(event); }
```

`AgentResilienceGuard` 的两个门槛是 180s 与 300s，同一拍命中很常见；命中时先发的
「卡死」在用户看到之前就被「内存」顶掉了。`costSpike` 等既有告警走同一条路径。

```rust
// 修后（engine.rs:440-462）
if self.latest_event.is_none() { self.latest_event = Some(event); return; }
if self.pending_events.len() >= 64 { self.pending_events.pop_front(); }   // 满了丢最早的
self.pending_events.push_back(event);
```

`clear_latest_event` 由「清空」改为「确认这一条、推下一条」；`EngineState` 新增
`pending_events`，前端角标显示「待确认 +N」。

## 可核验的行为证据

- **同拍两条都不丢**：`two_alerts_in_one_tick_both_reach_the_user` —— 先断言首条是「死锁」、
  排队 1 条；确认后断言第二条是「内存长期占用过高」且 `id` 不同（证明是两条独立事件，
  而不是同一条重复上屏）；再确认后清空。
- **走的是生产路径**：用例调用的是 `publish_guard_alerts`——`refresh` 内部调用的**同一个函数**，
  不是另写的测试专用代码，所以「接线到底接上了没有」是被真测到的。
- **开关真的关得住**：`the_anomaly_alert_switch_actually_gates_the_publication` ——
  关闭时一条不发（含 `pending_count() == 0`），打开后照旧发得出来。
- **队列有界且保留最新**：`the_pending_queue_is_bounded_and_keeps_the_newest` ——
  推 200 条后 `pending_count() <= 64`、队首仍是 `ev-0`、逐条确认后最后一条是 `ev-199`。
- **反向验证**：把 `push_event` 改回覆盖式 → 上面第一条用例红；还原后 **115 全绿**。
- **测试数**：Rust 112 → **115**、Swift 550（未动）；编译警告保持 **26**。

## 边界与后续风险

- **形态差异仍在**：Swift 是事件流（逐条 `publish`），Rust 是「一次一条 + 等用户确认」。
  用户长时间不点确认时，Rust 的告警会排队而不是全部铺开——`+N` 角标是缓解，
  不是等价物。已写进 23 号对照表。
- **满了丢最早的那条**：这是「有界」与「一条不丢」之间的取舍，我选了保留最新。
  真实告警频率（同类 10 分钟冷却）下永远碰不到 64 条上限，但**这个上限没有告警**，
  真被触发时是静默丢弃。数量级足够远，暂不加计数器；若日后告警来源变多应回头加。
- **引擎级端到端仍缺**（连续第三轮记着）：用例覆盖了「守护 → 事件队列 → 确认」，
  但「真进程跑满 5 分钟后 `is_hung` 变 true，然后 refresh 真的把它发出来」需要时间接缝
  （refresh 内部用 `now_ms()`，而造出「真进程高 CPU 五分钟」不现实）。
  今天能测的边界是：`is_hung` 规则（`health.rs` 6 条）+ 守护阈值与冷却（`resilience.rs` 7 条）
  + 本文的发布路径 3 条。真正没被覆盖的是**采样到快照的那一段**。
- **`demo` 模式的兜底事件**仍用 `if self.latest_event.is_none()`，与队列兼容（队首为空才补），
  未改。
- 同前几轮：同一人既改又审；真正的护栏是反向验证的那条红与三条判别性用例，不是这份文档。
