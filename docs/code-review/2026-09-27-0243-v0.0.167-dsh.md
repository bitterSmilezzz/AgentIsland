# v0.0.167 独立复核 · DSH · 2026-09-27 02:43

## 范围与结论

复核本轮三件：ADR 0011（本地状态存储口径）、`atomicfile.rs` 抽取 + `settings.json` 改原子写、
`ReadonlyDB` 补 `busy_timeout`。结论：两处缺口都是**真缺口且已修**，各自有能反向变红的用例；
ADR 的选型结论每条都有可点开的一手依据。Swift 侧只动两处，属冻结令允许的缺陷修复。

## 可核验的行为证据

- **`busy_timeout` 的行为用例是有效的，不是空转。** 用例真建库（回滚日志模式，WAL 下读写
  不互斥、锁根本不生效）、真在后台线程持 `BEGIN EXCLUSIVE`、200ms 后放锁；**反向对照**用一条
  不带 busy handler 的直连断言此刻必得 `SQLITE_BUSY`——没有这条，用例可能在锁没生效时静默通过。
  **双向验证**：把 `sqlite3_busy_timeout(db, busyTimeoutMs)` 摘掉重编，用例立刻红并给出
  `期望 [Optional("ok")] 实际 [nil]`；还原后 550 通过 0 失败。
- **原子写**：`atomicfile` 的四个用例（成功替换并 0600、校验失败保原文件+不留暂存、
  目标不存在时不创建、符号链接被拒）随实现一起迁到 `atomicfile::tests`，全部在跑。
  新增 `settings::tests::save_to_replaces_settings_atomically_and_leaves_no_staging_file`：
  用临时目录（**不碰用户真设置目录**）断言「写出来的能被解析回来」「目录里只剩目标文件」
  「覆盖写同样不留暂存文件」。
- **测试数**：Rust **73 → 74**、Swift **549 → 550**；`cargo test --locked` 与
  `Swift 测试门禁` 均 0 失败。`provider.rs` 自身的行为用例一条没删（只搬走了测 `atomicfile`
  的四个），`ProviderProfilePreview is never constructed` 这条警告经 `git show HEAD` 比对
  确认**改动前就在**，非本轮引入。
- ADR 里的选型依据均为一手材料（Turso COMPAT.md 的 Guarantee #4 原文、fjall README 的
  WARNING 原文、sled README 的自述、SurrealDB 官方许可证页、MongoDB 官方弃用页），
  链接直接写在表里，可逐条点开复核。

## 边界与后续风险

- **未做端到端验收**：`settings.json` 的原子性只验到 `save_to(dir:)` 这一层，
  没有跑过真实的 Tauri 设置页保存路径；`busy_timeout` 也没有在真实 agent 库上压过锁。
  这两条都属于「机制已证、集成未证」。
- **`settings.json` 的权限从 umask 默认（通常 0644）变成 0600**：这是复用 `atomicfile`
  的副作用（暂存文件统一 0600）。文件本身不含凭据（凭据在钥匙串），同用户读写，属收紧不算回归；
  但它是一次真实的权限变化，记在这里而不是让它悄悄发生。
- **测试脚手架的重复**：`only_target_remains` 现在 `atomicfile.rs` 与 `provider.rs` 各一份。
  只影响测试代码，没抽公共测试工具是有意的（避免为两个用例引入第三处）。
- **ADR 的两个阈值是工程量级，不是实测**：「约 1MB」「≥10⁴ 行」在 ADR 里已明确标注为
  可判定用的量级、真触发时按当次数据重估。不要让它们变成看起来精确的假数字。
- **同前几轮：同一人既改又审。** 真正的护栏是那两条会反向变红的用例（busy_timeout 行为用例、
  `atomicfile` 的保原文件用例），不是这份文档。
- 本轮**没有**触碰运行时存储：JSON 继续用，SQLite 读侧导入仍是 M3 的后续项；
  ADR 的三个触发条件一个都没到，也没有预先加抽象层。
