# v0.0.181 独立复核 · DSH · 2026-09-27 08:06

## 范围与结论

复核两件事：预算告警与月末预估的迁入（`budget.rs` / `forecast.rs` + 引擎接线），
以及**修掉一份「同功能两份实现」**（`engine::compact` vs Swift 唯一的 `TokenUsage.compact`）。
结论：口径照搬、接线可观察、漂移已消除。Swift 侧零改动。

## 可核验的行为证据

- **只有跨级才报**：`crossing_the_warning_line_alerts_exactly_once` /
  `crossing_the_exceeded_line_alerts_once_on_top_of_the_warning` /
  `a_direct_jump_from_normal_to_exceeded_reports_the_exceeded_alert_only`。
  **反向验证**：把 `last_notified_level < 1` 改成恒真 → 3 条用例同时红（含引擎接线那条）。
- **滞回在下一次越线时才起作用**：`only_a_fall_below_seventy_five_percent_rearms_the_alert`
  —— 76% 不重新武装，所以再冲上 80% **不报**；真回落到 <75% 后才再报。这条直接对应
  Swift 注释里记着的「按自然日重置导致每天午夜重复报」那个错误。
- **引擎接线**：`the_budget_alerts_once_per_level_crossing` —— 50% 无事件、82% 推「预警」
  （`system` /「Token 预算」/ `costSpike`，数字在 `detail`）、900k 不重复、150% 再推「超额」。
- **关掉告警只停事件**：`turning_the_alert_off_keeps_the_status_but_stops_the_events`。
- **清空预算要复位状态机**：`clearing_the_budget_rearms_the_tracker_...`
  （不复位的话，用户再设预算时会立刻收到一条旧级别的告警）。
- **手改配置的钳制**：`a_negative_or_absurd_budget_from_a_hand_edited_file_is_normalized_away`
  （负预算会让「超额」永远成立）。
- **预估的四段文案与钳制**：10 条用例，含闰年规则（1900/2000/2024/2026 的二月）、
  溢出饱和（`i64::MAX` 不 panic）、金额上限（`$1e9` 而不是 `Inf`）、负数钳 0、
  月末最后一天剩余 0 天。
- **compact 统一**：`thresholds_and_suffixes_match_the_swift_reference` +
  量级单调 + 负数为 0。**反向验证**：把 `k` 阈值退回 1000 → 5 条用例红
  （含预算文案，说明两份实现一旦分叉就会互相污染）。
- **测试数**：Rust **176 → 201**（+25）；**编译警告 26 → 25**（`format_cost` 因预估接出来
  而不再是死代码）。稳定性：连跑 3 次全绿。

## 本轮最有价值的部分：修掉一个真问题

Swift 全仓只有一份 `TokenUsage.compact`（卡片、悬停、热力图、详情页、CLI 都走它）。
Rust 侧却另有一份 `engine::compact`，与参考实现在三处不同：`k` 阈值（1000 vs **10000**）、
十亿后缀（`G` vs **`B`**）、尾零（剥 vs **保留 `12.00M`**）。
而它当时正用在一句 Swift 也用参考函数构造的告警里（`近 N 分钟约 X tokens/分钟`）。

两份实现同时存在时，「同一份用量在两处显示不同」只是时间问题——这不是风格问题，
是**同一份数据两个口径**。本轮统一到参考实现，并把旧用例改写成参考口径，
同时说明为什么原来的「`1.0k` 假精度」偏好被放弃（审美取向不足以支撑与参考实现分叉）。
唯一保留的差异（负用量钳 0）写在注释里，理由是可验证的：负用量只可能来自统计回绕。

## 顺带的发现（写进了代码注释，并有不变量用例守着）

Swift 预报的 `else` 分支（「按当前增速，预计月末消耗 …」）在「当天用量 > 日均预算」前提下
**数学上不可达**：设 T = 当月天数、B = 日均预算、D = 当天用量，D > B ⇒
`floor(B·T/D) ≤ floor((D−1)·T/D) = T − ceil(T/D) < T`；即使 `B·T` 饱和到 `i64::MAX` 也不行
（饱和要求 `B > i64::MAX/T ≥ D`，与 `D > B` 矛盾）。
Rust 保留同样结构以对齐，但用一条**覆盖 4 种月长 × 5 档预算 × 4 档用量 = 80 组参数的不变量**
证明它不会被走到（真走到就说明算术被改坏了）。

## 边界与后续风险

- **预算与预估都没有界面入口**：`dailyTokenBudget` 只能手改 `settings.json`；
  `token_forecast` 命令没有 UI 消费方（与 `remote_status` 等同一状态）。
  这一轮交付的是判定与接线正确，不是「用户能用」。
- **服务端的「24h 用量」是引擎缓存**：`token_forecast` 用 `grand_total`（与卡片同一个数，
  这是有意的），所以它依赖引擎在跑；引擎停着时会返回上一次的值而不是重算。
- **`compact` 的分桶边界没有跨语言实样对比**：我的用例是照 Swift 源码写的期望值，
  没有把 Swift 版的输出逐值 diff 过（那需要一个 Swift 侧的小程序）。风险低但确实是推断。
- **负用量钳 0 是有意差异**：若将来与 Swift 的输出做逐字对比，这一处必然不同——已写进注释与
  矩阵对照表，不是遗忘。
- 同前几轮：同一人既改又审；真正的护栏是两处反向验证的红与上述判别性用例。
