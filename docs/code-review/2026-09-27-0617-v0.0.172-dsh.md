# v0.0.172 独立复核 · DSH · 2026-09-27 06:17

## 范围与结论

复核判定增强组第二个模块：迁入 `AgentResilienceGuard`（持续死锁 / 内存驻留守护），
含默认开启的设置开关，并把 Swift 侧重复了两遍的 2GB 门槛收敛成一处。
结论：**口径逐条对齐，两条载荷性规则各有判别性用例**。Swift 侧零改动。

## 可核验的行为证据

- **阈值与文案**：卡死 180s、内存 300s、冷却 600s 三个常量与 Swift 同名值一致；
  `a_condition_must_persist_before_it_alerts` 断言 `180s - 1ms` 不报、`180s` 报，
  且文案逐字为「A 疑似死锁已达 3 分钟，建议点击逃生舱重置」。
- **两条载荷性规则**（各自有判别性用例，并**反向验证**过）：

  | 规则 | 用例 | 破坏后的表现 |
  | :--- | :--- | :--- |
  | 条件消失 ⇒ 起点与「上次告警」一起清零 | `recovery_clears_the_cooldown_so_a_new_episode_alerts_again` | 只清起点时用例红（`left: 0, right: 1`） |
  | 进程不在 ⇒ 该 agent 状态整份作废 | `a_stopped_agent_drops_its_state_and_its_cooldown` | 不作废时用例红（`left: 0, right: 1`） |

- **冷却与两类独立**：`a_second_alert_waits_for_the_cooldown` 断言冷却内不重复、冷却过后再提醒；
  `hung_and_memory_cooldowns_are_independent` 断言两个条件同时到点会各报一条（hung 在前）。
- **`None` 的口径**：`not_evaluated_never_starts_a_timer_but_does_clear_one` —— 判不出时**不开始计时**，
  但按 Swift 口径它**会清掉**正在计时的窗口，所以之后要重新凑满 3 分钟。
  这条是「`false` 与 `None` 不能混同」在守护侧的延伸。
- **内存文案带读数**：`memory_alerts_on_its_own_threshold_and_text` 断言消息里含 `2.4 GB`。
- **测试数**：Rust **105 → 112**（+7）、Swift 550（未动）；编译警告保持 **26**。

## 顺带收敛的重复口径

Swift 的 `AgentHealthEvaluator` 与 `AgentResilienceGuard` 各写了一遍 `2GB`（都叫 `twoGB`）。
Rust 侧原本把 2GB 写在 `health::evaluate` 内部，现已提为 `health::MEMORY_SEVERE_BYTES`，
健康度与守护共用——否则「健康度说『严重过高』」与「守护会不会告警」可以在同一个数值上分叉。

## 边界与后续风险

- **守护被接成默认开启，但开关只存在于设置文件里**：`auto_anomalies_alert` 与 Swift 同名项
  默认值一致（`true`），用户能编辑 JSON 关掉；但 Rust 今天**没有设置界面**，
  所以「关掉它」这条路对普通用户不可达。Swift 侧有界面开关。已写进对照表。
- **引擎级端到端仍缺**：与上一轮同样的缺口——`Guard::evaluate` 被 7 条用例覆盖，
  但「引擎真的在 refresh 里调它、并且事件真的进了 `latest_event`」没有用例。
  引擎 tick 用真实时钟，注入时间需要先做时间接缝。这一点在连续两轮里都记着，仍未做。
- **`latest_event` 一次只留一条**：`push_event` 是赋值而非队列，所以同一拍里若卡死与内存
  同时告警，界面上只会看到后一条（内存那条）。Swift 侧是 `publish` 逐条发。
  这是 Rust 事件管道的既有形状，本轮没有动它——**但它意味着「两条告警同时发生」时
  用户会漏看一条**，属于真实缺陷，应单独开一轮处理。
- **`TaskDurationTracker` 刻意未迁**：`record` 有接线处，`stats` 的唯一消费者是 Swift 的详情页，
  而 Rust 没有详情页。先迁会得到一个只有写、没人读的模块。理由已写进 CHANGELOG。
- 同前几轮：同一人既改又审；真正的护栏是上面两次反向验证的红，不是这份文档。
