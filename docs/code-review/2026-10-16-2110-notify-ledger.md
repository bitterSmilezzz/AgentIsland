## 结论

**2 项 P1、6 项 P2**，全部已修并复核；无未处理项。

### P1（已修）

| # | 问题 | 修正 |
| --- | --- | --- |
| 1 | **淘汰计数未兑现**。设计文档承诺「提供淘汰计数」，但 `EngineState` 没有该字段；更实质的是 `identities`(1024) 与 `pending`(64) 双 FIFO 不对称——第 65 条起在 `pending` 被淘汰，而 hash 仍留在 `identities` 内，于是该事件既不在内存队列、也不在恢复集、重放仍被永久判重，**且没有任何出口可观察** | `Ledger.evicted` 在 `pending` 淘汰处递增 → `EngineState.notify_evicted` → 通知页显示真值。语义定案并写进注释与文档：**正文淘汰 ≠ 身份遗忘**（已交付的事件不该因保留容量回收副本就复活），身份窗口 1024 条 |
| 2 | **`restart-app.sh` 的 SIGTERM 绕过写盘收尾**。脚本用 `pkill -f`（SIGTERM），默认动作直接终止进程，**不经过 Tauri 事件循环**，于是钉在 `RunEvent::ExitRequested`/`Exit` 上的账本收尾在这条路径上永不执行——而它恰是本仓库唯一规定的重启动作 | 改为先 Apple Event 优雅退出（等最多 8 秒），未生效才用信号兜底并明说「本次写盘收尾可能未执行」。已实测优雅退出确实生效 |

### 审查过程中实测出的既有缺陷（清单外，已一并修）

`cli.rs` 的 `notify` 发的是 `kind` 键，而生产路由只读 `event` —— 自 v0.0.205 起，
**所有 CLI 投递都被静默当成 `completed`**（`--kind attention` 印着「已投递」，队列里却是完成）。
同一函数里还有「400 也印已投递」。改法：抽出 `normalize_event_kind` 作为 `/notify` 契约的
单一来源（路由与 CLI 共用），CLI 改发 `event` 键、未知类型本地按用法错拒绝。

## 审查确认无问题的部分（不必重做）

- **落盘隐私闭环**：`StoredEvent` 只剩 6 个白名单字段 + `deny_unknown_fields`；外部 id 与深链 id
  一律哈希；`agent_id` 只留 builtin 档案 id 或 `system`/`external`；`decode()` 反向强制
  （非法哈希、非白名单 agent、未知字段一律判无效文件，旧格式无法被重新解释）
- **并发**：判重在引擎锁内串行；worker 单线程取 `latest.take()` 快照
- **revision / 写盘失败不谎称已保存**：失败只更新 `status`，`saved_generation` 不推进
- **新事件不漏报**；恢复不重新外发；`publish` 不持锁做 IO（`engine.state()` 不会被磁盘 IO 阻塞）
- **退出链**：托盘退出 / Cmd+Q / 窗口全关三条路径都会执行 flush（已逐环实读 tauri / tao 依赖源码）

## 仍存的不确定（作者已如实记录，非隐藏）

- 写盘前异常退出可能丢最近入队或复活最近 ack；正常退出 2 秒限时收尾，超时即放弃并记录
- `notify_conflicts` 只在内存，重启后首条重新胜出、计数清零
- 无 id 兜底只区分「同秒同内容」，不是跨秒 exactly-once 承诺
- 未做断电/强杀、磁盘满、跨平台实测
