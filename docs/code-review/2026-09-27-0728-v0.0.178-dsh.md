# v0.0.178 独立复核 · DSH · 2026-09-27 07:28

## 范围与结论

复核两件事：把外发从采样线程挪到工作线程（`dispatch`），并按 Swift 口径补上失败重试；
另修掉一个我自己在上一轮引入的并行测试端口竞争。结论：**不阻塞与重试两条都真验证过**，
套件从「3 次红 2 次」恢复到连跑 6 次全绿。Swift 侧零改动。

## 可核验的行为证据

- **dispatch 不阻塞（本轮核心）**：`dispatch_returns_immediately_even_when_the_transport_is_slow`
  —— 假传输睡 300ms，`dispatch` 必须在 100ms 内返回，随后账本由工作线程回填。
  **反向验证**：把 `dispatch` 改成同步调用 → 用例红，且报出的正是
  `实际等了 310.999625ms`（传输的延迟原样出现）。
- **重试一次且留痕**：`a_retryable_failure_is_retried_once_and_the_tries_are_recorded`
  —— 脚本化传输先失败后成功 → `tries == 2`、文案「已送达（重试 1 次后）」。
- **两类不重试**：`a_permanent_rejection_is_not_retried`（`calls == 1`，
  文案带「对端明确拒绝，重试无用」）与 `a_test_send_is_never_retried_because_the_user_is_watching`。
- **占位在重试期间仍握着**：`the_throttle_slot_stays_claimed_while_the_retry_is_in_flight`
  —— 真并发：工作线程占位后从另一线程发同一键 → 必须「节流命中」。
  **反向验证**：把撤占位提到重试之前 → 该用例红（并发事件挤了进来）。
- **测试数**：Rust **162 → 167**、Swift 550（未动）；编译警告保持 **26**。

## 顺手修掉的并行测试竞争（值得单列）

上一轮我用「绑定端口后立刻释放」来造「已关闭端口」。在并行跑的套件里，这个端口会被
**别的用例立刻抢走**，于是连接成功、报的错变成 `TLS 握手失败：I/O error.` 而不是「连接失败」。
表现是 **3 次里红 2 次**——我第一次跑全量时看到的那条「166/167」就是它。

修法：改连 **1 号端口**（特权端口，测试不会去绑），拒绝连接是确定性的；
并发探针也从「睡固定 80ms」改成「轮询占位是否落下」。修完连跑 **6 次全绿**。

**这条比缺陷本身更值得记**：间歇性红的用例会训练人忽略红色，比没有用例更糟。

## 边界与后续风险

- **线程模型是有意的「一次外发一个线程」**：外发是低频动作（同类有 90 秒节流），
  不值得为它引入线程池。若日后告警来源变多、或要做并发上限，这里要重看。
- **`Arc<Mutex<Inner>>` 的锁只在极短临界区持有**（claim / release / record），
  传输调用不在锁内。这一点没有专门用例守——它靠「`attempt` 在锁外调 transport」的代码形状，
  改动时容易退化（例如把整段 `attempt` 包进锁里就会让并发探针变成串行等待，用例仍会过）。
  **这是本轮最薄的一处**：没有「锁未被长期持有」的断言。
- **进程退出时在途的外发会消失**：线程不是 join 的。Swift 侧 async Task 有取消语义。
  今天的场景（低频告警）代价可接受，但没有记录。
- **重试间隔是硬编码的 5 秒**（`RETRY_DELAY_MS`），与 Swift `retryDelay` 默认值一致；
  用户不可配（Swift 也是构造参数，生产同样写死默认值）。
- **仍缺**：SMTP over 465 会话（含 `smtp_line`）、钥匙串、真实公网证书链实样。
- 同前几轮：同一人既改又审；真正的护栏是三次反向验证的红与上面几条判别性用例，不是这份文档。
