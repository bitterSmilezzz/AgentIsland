## 审查结论（原文要点）

> 未发现 `timestamp` 语义变化破坏现有业务逻辑，但当前指标存在来源混入、起点偏晚、
> 慢样本被剔除和生产结果不可读取等问题，尚不能据此可靠判定 hook 入队是否达标。
> 另外发现一项测试可能错误通过、一项测试存在偶发失败风险。

审查者独立核实并**确认无问题**的部分（这些不必重做）：

- `AgentTaskEvent.timestamp` 全部 4 处直接读取：`audit.rs:284`（仅展示）、
  `engine.rs:926`/`953`（均在 `notify_outbound` 的 `externally_delivered` 闸门之后，
  webhook 事件到不了）、`engine.rs:882`（本次新增）。
- `saturating_sub` 不会把普通负差值截成 0：负值仍被 `record()` 拒绝并计数。
- 最近秩 p95 公式在 n=1/20/21/100/1000 均等于 `ceil(0.95n)`，无 off-by-one。
- 与 `TaskDurationTracker` 的「引擎持有 + 不加锁 + VecDeque 丢最早」约定一致。
- 序列化与前端消费：`app/ui` 不读 `timestamp`；去重按 agent/类型/指纹；
  审计耗时列读 `event.duration`。

## 审查未列出、但本轮发现并修掉的结构性问题

审查提到「生产 channel 只在 `main.rs:3244` 消费，循环末尾按 2 秒/5 秒休眠，
**即使修复测量问题，现有调度也不能保证 ≤1 秒**」，并把它留给后续决策。

本轮判定这是**必须修**的：不修的话指标只是如实报告一个设计限制，需求本身仍然不成立。

- **修法**：`engine_loop` 从 `sleep(interval)` 改为 `wake_rx.recv_timeout(interval)`；
  本地入口成功入队一条事件后 `wake.send(())`。
- **一个必须处理的分支**：所有 sender 被丢弃后 `recv_timeout` 立刻返回 `Err`，
  若不管就会变成不带 sleep 的空转循环、直接跑满一个核。已显式处理
  `Disconnected` → 退回纯 `sleep`。
- **验证**：`a_real_http_request_reaches_the_queue_within_the_target` 绑临时端口
  （`127.0.0.1:0`，不碰真实配置目录）发**真实 HTTP 请求**，断言 p95 ≤1000ms。
  **变异验证**：把入队时间人为 +2000ms，该测试立刻失败并打印「实测 2002ms」。

## 仍未验 / 局限（如实记录）

- **未在真实 GUI 进程里量过实际 p95**。HTTP 入口只在常驻 GUI 起（`isolated_instance_requested`
  的几种诊断模式都不起它），本轮未启动真实应用去压测，故**不声称「本机实测 p95 = N ms」**。
  已给出读取路径（`EngineState.notify_latency`），需要时可在真实进程内取证。
- 指标只覆盖三条即时性要求里的**一条**（hook → 入队）。另两条
  （来源事件→桌面提醒、外发入队→首次发出）需真实采样源与网络，未实现。
- `automation.break` 的偶发失败（前几轮记录）与本轮改动无关，仍未定位。
- 未提交、未推送、未发版。

## 验收口径更正（后续复核追加）

上文把 `a_real_http_request_reaches_the_queue_within_the_target` 称为完整端到端验收，证据不足：当时测试只发一个 HTTP 请求、确认唤醒，再由测试手动消费队列，没有运行生产等待/消费调度；一条样本也达不到统计模块的 20 条判定门槛。2002ms 变异只证明慢样本会被拒绝，不能证明移除生产唤醒后测试会失败。

当时唤醒使用无界 channel，每条事件都能积累一个唤醒令牌，缺少突发合并。`ALL VERIFIED` 仅证明可用检查通过，输出明确仍有五类外部环境验收未执行。上述记录保留为当时证据，最终产品交付以另附的当前构建、生产路径测试及独立复审为准。
