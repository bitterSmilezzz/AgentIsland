# 内存误报修复复查

## 可失败的复现

cargo test --locked --manifest-path app/src-tauri/Cargo.toml stable_high_memory：修复前两个用例失败。稳定 4GiB、CPU 5% 被健康度扣到70分；稳定4GiB连续采样在300秒产生告警。复现直接调用生产 health/Guard 路径，无真实用户进程或数据依赖。

## 实现与复核

- 删除仅凭1.5/2GiB扣健康度分与2GiB持续驻留告警。高RSS本身不推断泄漏。
- Guard保存有界时间序列，连续两段约5分钟各增长512MiB且25%、当前至少2GiB、无明显回落才给出增长信号。PID变化、进程停止、读数缺失、时钟倒退、超过30秒的间断重建基线。0.5秒采样下1280条覆盖完整窗口；中间边界允许一个采样间隔的误差。
- 引擎通知和快照健康度使用同一份 MemoryGrowth。关闭异常通知仍观测内存趋势，原疑似卡死通知开关和重新计时语义保持。
- 原“防爆保护建议重置”“长会话泄露隐患”改为实际增长事实与检查建议，不证明泄漏、不要求重启。
- 自查修正临界波动清冷却问题，内存信号短暂不满足时保留冷却，避免反复提醒。疑似卡死冷却保持独立。

## 验证

完整 Rust 回归结果在最终检查后记录。覆盖稳定高占用、加载后平台、小幅波动、单次子进程跳升、连续增长、稀疏采样、进程生命周期、时钟倒退、不等间隔采样、通知冷却、卡死与内存通知独立、通知关闭时的健康度趋势。更新既有双告警队列测试，使用密集增长观测，不再把常量内存视为异常。

复核发现 CLI 异常扫描另有固定 2GiB 的清理候选规则，已删除并抽出生产路径的纯判定；补充高 RSS 不列为清理对象、独立卡死判定仍有效的行为回归。正式构建、重启与 release 门禁结果在完成后补充。不以当前资源读数判断用户应用是否“有泄漏”，也未设置按品牌豁免异常的白名单。
