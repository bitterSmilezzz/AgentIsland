## 一次收回结论的教训（本轮最该记住的）

我**从截图判断**「输入框横向溢出、内容列被挤扁」，并据此准备改 flex 的 `min-width`。
加了一行度量之后：`bodyScrollW=192`、`widestInput=172`（< 192）——**根本没有溢出**。
我看到的是**纵向滚动条**与被截断的占位文案（长 placeholder 在窄字段里被裁，是正常的）。

更早的一版度量还**量错了地方**：它跑在注水之前，量到的全是「加载中…」骨架，
于是四个路由的数字一模一样、看起来「都没问题」——**度量本身也要验**。

两条合起来：**别用眼睛（尤其别用一张被别的窗口盖住一半的截图）下布局结论；量一下只要一行。**

## 顺带修掉一条随机拦人的门禁（本次发版第一次跑就被它拦下）

`引擎: setEnabled 后重采样走后台路径`：断言「`setEnabled` 返回时扫描次数没变」，
而假 provider 的扫描是瞬时的 ⇒ 后台那一拍可能在断言前落地。**实测 5 次红 3 次**。

- 第一版修法（给假 provider 加 150ms 延迟）：1/10，**仍会红**——测试线程被抢占超过延迟时照样落地。
- 最终修法（**标记判据**，与调度无关）：调用方在 `setEnabled` 返回后置位；provider 记录
  「返回前落在主线程的扫描次数」。**15 次连跑全绿**。
- **反证**：把同步主线程扫描放回 `setEnabled` ⇒ 立刻红（`期望 [0] 实际 [1]`），
  即**去抖动没有削弱守卫**。（第一次反证的补丁锚点匹配失败、根本没应用，
  那一轮的「通过」不算数——重做才成立。**反证本身也要验它真的改到了代码**。）
