# v0.0.165 独立复核 · DSH · 2026-09-27 01:15

## 范围与结论

复核 `scripts/scan-secrets.sh` 的历史扫描路径。结论：修复前存在**跨进程假绿**——
同一个工作区里第二次运行会复用第一次枚举出的对象流，新提交的 blob 全部漏扫，
而输出照样打印通过。本轮把它改成进程内备忘，并补一条守护。Swift 侧零改动。

## 可核验的行为证据

- 症状实测（真仓库，未清理 `/tmp`）：门禁报 `2172` 个 blob，而
  `git rev-list --objects --all | ... | awk '$2=="blob"'` 实测 **2199**。
  差额 27 正是 v0.0.163 与 v0.0.164 两次提交新增的 blob。
  定位到 `blob_stream()` 的 `[[ -s "$BLOBSTREAM" && -s ... ]] && return 0`：
  键是 `/tmp` 文件是否存在，而 `blob_stream()` 每轮只被调用一次（`:178`），
  所以该判断在单轮内一次都省不到，唯一效果就是跨轮复用。
- 冷缓存重扫（`rm` 掉三个中间文件）：报 `2199`，`cred_prefix` / `private_key`
  零命中、其余三类命中全在已核准豁免内、棘轮基线未放宽。即那 27 个 blob **本来也干净**。
- 修复后连续两轮：均报 `2199`（等于真值），不再随 `/tmp` 残留漂移。
- 守护有效性**双向验证**：新增第 8 条用「提交后 blob 计数必须变大」判定。
  对修复前的脚本（`/tmp/scan-secrets-OLD.sh` 备份副本）实测变红
  （`first=4 second=4`）；对修复后的脚本通过。套件 7 条 → 8 条，8 通过 0 失败。
- 为什么值得修：工作区扫描 `grep -InHE`（`-I` 跳过二进制），历史扫描 `grep -a`
  （不跳）。「新提交的二进制文件里有没有东西」只有历史这一遍能回答；历史扫描同时
  是覆盖「已改掉/删掉的旧 blob」的唯一一遍。

## 边界与后续风险

- 三个中间文件（`scan-secrets-hits.txt` / `-files.txt` / `-shas.txt` / `-paths.txt` /
  `-blobs.txt`）仍共用固定 `/tmp` 路径。测试夹具会在真仓库的 `/tmp` 上覆盖它们。
  修复后每轮都重新生成，**判定正确性不再受影响**，但并发或中断场景没有隔离保证，
  本轮未做（例如把根目录改成 `mktemp -d` 或可注入变量）。
- 新守护只证明「对象流被重新枚举」，不证明「新增 blob 的内容真被判过」。
  覆盖后者需要往夹具里放一个形状可控的合成命中，会引入新的假凭据字面量，
  本轮刻意没做——用计数断言已能锁住这个回归面。
- `/tmp` 目录本身不属于仓库，`scan-secrets.sh` 的中间态在 CI 上每次全新，
  这个假绿在 CI 上是隐性的；它主要伤**本机连续发版**的场景，正是本项目的主用法。
