## 一次「实现是对的、期望是错的」

`ids_never_collide_...` 第一版叫 `..._do_not_reuse_freed_numbers`，断言删掉 `2` 之后
新条不该再用 `2`——**红了，错的是期望**。「现有最大值 + 1」防的是撞号（`len + 1` 会撞：
`[1,3]` 的下一个是 `3`），而**复用已删号在待办里无害**：界面每次按完整快照重画，
不存在「拿着旧 id 的陈旧引用」；要真的不复用，就得在文件里多存一个计数器，
那点复杂度换不来任何东西。用例已改成断言真正该保证的性质（不与现存 id 重复），
并把这段取舍写进注释——**把「我原本以为的规则」也留在代码里**，
下一个人就不会再写一遍同样的错误期望。

## 顺手清理：没人调的 API（警告 21 → 16）

- `todos::list` / `todos_path`：命令走 `snapshot`，两个都是多余的（删）。
- `provider.rs` 的 `MaskedSecret` / `ProviderProfilePreview` / `REDACTED`（v0.0.160 建的）：
  删的理由**不是**「用不上」，而是**保护方式换了**——档位结构里没有承载密钥的字段
  （只存 `env_key` 变量名），校验还会在门口拒绝「像密钥的长串填进 env_key」。
  留着一套没人调的掩码类型，会让人以为「密钥是被掩码保护的」，
  而真实情况是「密钥压根进不来」——**假的安全感比没有安全感更糟**。
  这句话连同删除理由写在原处，真需要显示掩码时历史里有它。

## 边界与后续风险

- **像素未验证**（同前几轮）：本轮最大的未验证面。
- **没有对用户真实的 `todos.json` 写入过**：用例与自检都在临时目录里；
  启动读路径不创建文件（已实测）。第一次真实写入是使用者的动作。
- **角标的刷新时机**：启动读一次，之后每次增删改由返回值就地更新。
  **没有**监听文件变化——如果有人手改 `todos.json`，角标要等下次进页面才更新。
  这在单人单机场景下可接受，但值得记着。
- **`update_codex_profile` 现在是死代码**（v0.0.189 被 `plan_codex_apply` 取代，
  但它还有「清掉 provider 覆盖」这个独有的行为，没接出来）。已记入 Phase 4：
  要么接成「回到 Codex 默认」的动作，要么删掉并把该行为记为不做。
- **待办页的错误提示是 Toast**：与档位页同一问题（失败不静默，但只存在一瞬间）。
- 同前几轮：同一人既改又审；真正的护栏是两处反向验证与那次「期望写错」的自查。
