## 先核实事实（这一轮的第一件事）

开工前没有照抄记忆里的形状，而是取了两处一手证据（[研究记录](../research/2026-09-27-codex-provider-config.md)）：

- 本机实扫 `~/.codex/config.toml`：**只打印键路径**，键名含敏感词的值一律省略
  （`auth.json` 是凭据载体，全程没有读过）。
- OpenAI codex 仓库 `docs/config.md`（提交 `3f40fbc`）原文。

两个结果改变了设计：

1. **本机没有 `[model_providers]` 段**，而 `01-current-state.md` 里 09-25 的快照说有——
   那份已过期，已按本次实样更正。
2. **Codex 自带档位层**（`[profiles.<name>]` + 顶层 `profile`）⇒ 切换只需改选择键，
   不必重写整份配置。写入面越小，越不容易碰到用户自己写的东西。

## 可核验的行为证据

- **顺序（先备份后写）**：`a_failed_backup_leaves_the_config_untouched`
  —— 备份路径先占成符号链接（`atomicfile` 拒写）⇒ 报错且配置**逐字节不动**。
  **反向验证**：改成先写后备份 → 红（「备份失败却把配置改掉了：用户既没备份、配置又被动了」）。
  这条用例的存在本身是个教训：**早先我把顺序改反，全套测试仍然通过**——
  说明「先备份后写」当时没有任何东西守着。
- **备份-还原往返**：`applying_a_profile_backs_up_and_restores_byte_for_byte`
  —— 备份内容 = 改动前原文（逐字节）；一路改坏后还原，回到原样。
- **不半截写**：`a_broken_existing_config_is_never_half_written`——原文是坏 TOML 时拒绝写入，
  原文件不动且**暂存文件没留下**。
- **路径护栏**：`only_a_real_codex_config_path_may_be_written`——`auth.json`、
  别处同名 `config.toml` 都不是合法目标。**反向验证**：去掉护栏 → 红。
- **档位校验**：`a_bad_profile_is_rejected_before_it_can_touch_the_config`
  —— 空 model、id 带空格、非 http 的 base_url、不认识的 wire_api、小写 env_key、
  **像一整串密钥的 env_key** 全部在碰配置之前被拒；空展示名回落 id。
- **用户的额外键不被删**：`applying_twice_keeps_the_users_extra_provider_keys`
  （`request_max_retries = 7` 仍在）。
- **格式保留**：既有用例 + 新用例都断言行内注释、数组缩进、无关表原样保留。
- **库行为被钉住**：`a_new_root_key_lands_before_the_first_table`——
  TOML 里「表后面的键属于那张表」，库若把新根键排到表后会**静默挂错**。
  实测 `toml_edit` 插在第一张表之前；这是**库行为**，换版本可能变，所以留成回归用例。
- **DTO 无密钥**：`the_outbound_profile_shape_carries_no_credential_shaped_string`
  —— 不再拿分隔符切整段 JSON（第一版就是这么错的，把键名 `"name"` 判成可疑串），
  改为遍历 JSON 的**字符串值**，断言没有「长且纯字母数字」或已知前缀（`sk-`/`ghp_`/`AKIA`…）的串。
- **工具集不失控**：`the_tool_scan_only_promises_codex`（Phase 2 第 4 条：阶段内只做 Codex）。
- 测试 Rust **254 → 267**；编译警告 **21 → 19**。

## 一次偶发失败（如实记录，未确诊）

还原后第一次跑出现 `263 passed; 3 failed`，随后连跑 **10 次全绿**，重放当时的命令序列也全绿。
无法复现。我按最可能的机制修了：**并行用例的沙箱命名撞名**——`as_nanos()` 在 macOS 上分辨率粗，
两个线程可能取到同一个值，两个用例共用一个目录，先结束的那个 `Drop` 删掉另一个的文件
（症状正是「某次挂几条、再跑全绿」）。`provider.rs` 与 `tokens.rs` 的沙箱都补了进程级序号，
`tokens.rs` 里我还把重复实现的两份沙箱合并成一份（「命名要带序号」这件事只能有一个地方知道）。

**这是「假设 + 修复」，不是确诊**：我没有抓到那 3 条失败的名字，
也没有构造出复现。写在这里是为了不让它变成一笔糊涂账。

## 边界与后续风险

- **界面未做**（Phase 2 第 3/6 条的界面部分）：8 条命令今天没有消费方，
  能力边界文案 `PROVIDER_LIMITATIONS` 已经就位但还没人显示它。
- **没有对真实 `~/.codex/config.toml` 做过端到端切换**：所有用例都在沙箱里跑。
  第一次真实切换应当先看一眼备份目录里是否落下了文件。
- **`env_key` 只存变量名**：这符合 AGENTS.md 的零凭据红线，但也意味着
  「切了档」不等于「密钥就位」——用户仍需自己把变量设好。这条已写进能力边界文案。
- **`scan_tools()` 只承诺 Codex**：别的工具等的不是实现，是各自的一次核实。
- **`toml_edit` 的两条库行为**（根键插入位置、保留 decor）已被用例钉住，
  但升级依赖时仍应把这两条当成「要复核的契约」而不是「理所当然」。
- 同前几轮：同一人既改又审；真正的护栏是两处反向验证、以及那条**暴露出「顺序没被覆盖」**的新用例。
