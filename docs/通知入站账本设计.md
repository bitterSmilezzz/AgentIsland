`schedule`/`chief` 会被 `/notify` 以 400 拒绝。现已补齐，类型总数为 **8**：

| 类型 | 需求对应 | 触发者 |
| --- | --- | --- |
| `completed` | 完成 | 既有 |
| `attention` | 确认 | 既有 |
| `costSpike` | （资源/Token 告警，既有能力，保留） | 既有 |

**同步点（漏一处即真实失效，各有测试钉住）**：

1. `remote::EventKind`（枚举 + `parse` + `as_str` + `ALL`）——`ALL` 与 `parse`/`as_str` 互查。
2. `remote::Policy` 的逐类外发开关 `send_*` + `wire_value` 的 camelCase↔snake_case 别名。
   **别名必须逐类测**：camelCase 那一侧直接命中，掩盖别名缺失，只有 snake_case 落盘才会暴露。
3. `webhook::normalize_event_kind`（生产路由，未知值仍 400，不折叠）。
4. `notify_ledger::normalized_kind`（持久化身份投影，细分类型参与幂等分域）。
5. `notify_ledger` 的 `decode()` 合法类型白名单——**漏了会让含新类型的账本被判无效文件、永久停写**
   （本轮实测：新增五类后落盘被拒，`flush` 一直返回 false）。
6. `render::render`（外发标题）与 `app/ui/js/views.js`（界面摘要与 banner 前缀）。
7. 共享契约夹具 `tests/fixtures/contracts/notify-keys.json` 的 `event_kinds` /
   `event_kind_switches`。`event_kinds` 由 Rust 与浏览器两侧共读；`event_kind_switches`
   记 UI 实际使用的 snake_case 开关名，由 Rust 断言「关掉它只影响这一类」+ 浏览器断言
   「开关真的渲染出来」（否则用户关不掉新类型的外发）。
8. `audit.rs::event_type_text`（导出报告的类型列）与 `models.rs::AgentTaskEvent::summary`
   （报告摘要）——两处各有 8 类文案，漏一类就会把该事件写成「任务完成」。
9. `main.rs::deeplink_event_type`（深链 `notify` 的 `type` 参数）——**第三个**接受事件类型的入口。
   它没有「400」可回给用户，因此未知值仍回落 `completed`，但**已识别的 8 类一律保留细分**。
10. `cli.rs` 的帮助文本与参数校验：只接受 `--kind=`/`--agent=`/`--message=` 三种等号形式，
    其余（空格形式、单横线、拼错前缀）一律拒绝——它们都会被静默忽略并 fallback 成默认值。

**刻意不扩的边界**：`app/ui/js/task-attention.js::taskCoversEvent` 仍只认 `attention`。
它回答的是「任务关口上这条待处理项，是否就是当前这条事件」，而任务关口只承载**确认**；
把它放宽到全部提醒类会让一条 `failure` 被误当成关口的确认项。其余提醒类由
`views.js::isAlertEvent` 统一进入卡片、收起态摘要与窄条提醒。

**语义边界**：未知类型仍被 `/notify` 拒绝（400）而不是静默折叠——调用方需要知道自己发错了。
持久化投影对**未知**类型折叠为 `completed`，但对已识别的 8 类保持细分，使「同 id 换类型」
成为新事件而非重放。

## 缺口现状（核实过）

- `/notify`、`/event` 每次请求都生成新id并发送。重复请求会重复入队；hook带externally_delivered，既有外发闸门会抑制外发，不能声称它已造成重复外发。内部事件仍须在外发前统一判重。
- `push_event` 只做 `pending_events` 的 64 条有界淘汰，没有去重。
- 待处理通知只在进程内存：**重启即丢**，与「可追溯」不符。
- 既有 `dedup.rs` 是**会话信号**去重（键 `agent+kind+raw`，由 `decide_level` 消费），与入队幂等是两套身份空间，不能共用同一个 512 条队列——否则一次 hook 突发会把 attention 记忆挤掉，削弱 SUP-02「同事件不重报」。

## 设计

新增 `app/src-tauri/src/notify_ledger.rs`，一个 `Ledger` 持两项有界状态：

1. `identities: VecDeque<String>`（SHA-256 十六进制，CAP 1024）——入队幂等。
2. `pending: VecDeque<StoredEvent>`（CAP 64，与引擎待发队列同口径）——重启恢复。

- **身份**：客户端可在 `/notify`、`/event` 传 `id`（非空、≤128字节、ASCII安全字符）；显式ID按agent与规范事件类型分域，相同agent/类型/id首条保留，重试不覆盖正文，不同agent同id分别入队。无id时按agent、类型、正文、详情、到达秒计算SHA-256兜底：同秒同内容抑制，不同秒视为新事件。该兜底无法区分同秒同文的两个独立事件，可靠接入方须提供稳定id；不是永久或跨秒exactly-once承诺。
- **隐私投影**：恢复账本只存哈希身份、事件类型、时间、受支持档案标识及静态展示信息。原始id、任意agent名称、message/detail、会话正文、路径和凭据均不落盘。未知agent恢复为固定外部来源标识。恢复后只显示安全摘要，正文仍在来源工具，不能复制私密内容建立历史。
- **落盘**：`settings::config_dir()/notify-ledger.json`，0600、原子发布、revision 外部改动校验、字节上限、`schema_version`；损坏/未来格式**保留原字节**并永久停写（不删用户文件），reload 时内存仍可用。
- **持久化只在常驻 GUI 启用**，与 `enable_dedup_persistence` 同条件（`!demo && !isolated_instance_requested() && !background_test_requested()`）。
- **判重位置在引擎入队点**（`push_hook_event`/`push_event` 的入队分支），不在 HTTP 线程：HTTP 线程若为判重去锁引擎，会把刚量好的入队延迟重新拖慢（引擎锁可能在 `tick()` 里长持）。
- **id 复用冲突**：同一显式 id 带上不同 payload（message/detail/agent_name/duration/externally_delivered 指纹不同）时，**首条保留**，不另发第二条，并把冲突计入 `notify_conflicts`（`EngineState` 出口，界面显示「id 复用冲突」）。该计数只在内存，重启后首条重新胜出。payload 指纹与身份同一套长度前缀 SHA-256（不再用 64 位 `DefaultHasher`）：指纹只做内存内相等比较，但一次碰撞的后果是**静默**的——两条真不同的正文会被当成重放，第二条不入队、冲突计数也不动。
- **淘汰计数**：`pending` 超出 64 条时 `pop_front` 掉最早一条，并把次数计入 `notify_evicted`（`EngineState` 出口，与 `notify_duplicates`/`notify_conflicts` 同风格；同样只在内存，重启后从 0 起算）。该计数是唯一能读到「入队过、但已不在显示/恢复队列里」的出口。
- **正文淘汰 ≠ 身份遗忘**：`pending`(CAP 64) 是显示/恢复队列，`identities`(CAP 1024) 是幂等窗口，两者宽度**刻意不同**。第 65 条起正文被淘汰，但身份通常仍在 1024 窗口内，于是一次重放**仍判重**（计入 `duplicates`，不再入队、不改 `evicted`）。这是选定语义：已经交付给用户的事件不该因为保留容量回收了副本就复活；要抹掉身份得等它滑出 1024 窗口——狭窗口是有界的，不做「永久不重报」承诺。两条丢弃路径都可见：丢正文记在 `evicted`，丢身份由窗口本身说明。
- **落盘为白名单投影**：`StoredEvent` 用 `deny_unknown_fields`，字段固定为 `id`/`agent_id`/`event_type`/`timestamp`/`duration`/`externally_delivered`。`id` 一律为 SHA-256（含外部 `id`、`push_event` 与深链），`agent_id` 只保留已声明 builtin 档案 id 或固定 `system`/`external`（未知 HTTP agent → `external`），`event_type` 归一为 `attention`/`completed`/`costSpike`。未知字段、非法哈希或非白名单 agent 一律判为无效文件。
- **恢复文案**：`message` 固定为 `重启恢复的提醒，原始正文未保存，请查看来源`，`detail` 为 `None`；`external` 事件的 `agent_name` 显示「外部投递」。恢复不复制私密正文。
- **持久化状态**：`EngineState.notify_persistence`（`enabled`/`healthy`/`pending`/`saved`/`blocked`/`error`/`generation`/`attempted_generation`/`saved_generation`/`failures`，与 `EngineState` 其余字段同为 snake_case）区分「尚无保存记录」「待保存」「已保存」「保存失败」「读取失败或被外部改动，已停写」。写盘失败只增加 `failures` 与 `error`，不推进 `saved_generation`——「尝试完成」不等于「已落盘」。
- **退出 flush**：`Ledger::flush_handle()` 暴露只读 `FlushHandle`；Tauri `RunEvent::ExitRequested`/`Exit` 在**引擎锁外、不派发主线程**的前提下 `shutdown(2s)` 限时等待，超时写日志且不无限挂起；`Writer::drop` 不再 join 无界（detached 引擎持有时也能独立完成 flush）。

## 诊断 CLI 契约（隔离进程重启验收）

`agentisland --notify-ledger-probe <fixture-dir> <phase>`，`phase ∈ {1,2,3}`：

- 必须是**绝对路径且位于系统临时目录下**的真实目录；phase 1 要求空目录（探针写入 `.agentisland-notify-ledger-probe` 所有权标记），phase 2/3 只接受标记与 `notify-ledger.json`。
- 只使用生产 `LocalEventServer::bind_http("127.0.0.1:0")` + `serve_bound` + `HookScheduler` + `Ledger`，`ActivityEngine::notification_probe` 不枚举进程、不读用户配置、不读会话、不打开 GUI、不外发、不 `prepare_token`。
- 每阶段真实 HTTP 投递 `/notify` 并读取回执，stdout 输出单行 JSON：`schemaVersion`/`phase`/`pid`/`restoredPending`/`restoredSafe`/`httpAccepted`/`pendingBeforeAck`/`duplicates`/`conflicts`/`evicted`/`samples`/`pendingAfterAck`/`hashes`/`hashesAreSafe`/`diskHasPrivateText`/`flushSaved`/`generation`/`savedGeneration`/`failures`（仅数字、布尔与哈希，不含正文）。探针从不超过保留容量，故 `evicted` 必须为 0——非 0 就说明有正文被丢而回执仍称其为待确认。
- 失败退出码 2 并只在 stderr 给一句原因；诊断运行不写应用日志文件。
- 脚本 `scripts/test-notify-ledger-restart.py --binary <path>` 依次跑三阶段并校验 0600 账本不含私密正文与原始 id。
- **响应语义**：HTTP 返回「受理」（accepted），不宣称已投递；判重结果体现在状态里，符合仓库「受理≠收到≠已读」口径。
- **延迟样本**：只有真正入队的事件才记样本（与既有 `non_hook_events_do_not_feed_the_hook_metric` 的「样本=已入队」一致）；被抑制的重复单列计数，可见而非静默丢弃。
- **重启恢复**：启动时把已持久化的pending摘要还原进latest_event/pending_events，不重新外发；ack移除对应摘要。异步写盘前异常退出可能丢最近入队或复活最近ack，界面须显示待保存/已保存/失败/停写，不能将HTTP受理当作持久化成功。正常退出接入实际Tauri退出路径，在引擎锁外限时flush；三次独立进程验收投递→重启恢复并ack→再重启不复活。
- **容量**：内存与恢复统一最多64条未确认事件（包含队首）；超过容量按既定有界策略淘汰最早，并把淘汰次数计入 `notify_evicted`（`EngineState` 出口），避免宣称无限不丢。容量与身份是两个宽度不同的界：`pending`(64) 掉的是**正文**，`identities`(1024) 掉的是**身份**；正文被淘汰后重放仍判重（见上「正文淘汰 ≠ 身份遗忘」）。并发验收区分232条逐条确认无串号（32条真实 TCP + 200条路由直调），与200条未确认突发最终仅保留最近64条。

## 验收场景（正例 + 负例）

| # | 场景 | 期望 |
| --- | --- | --- |
| 1 | 同一 `id` 连发 2 次 | 只入队 1 条；重复计数 +1；延迟样本只 +1 |
| 2 | 换 `id`、同内容 | 两条都入队（不能把不同事件误判为重复） |
| 3 | 无 `id`、同内容同秒重放 | 判为重复（服务端指纹兜底） |
| 4 | 写入后重建 Ledger（模拟重启） | 旧身份仍判重 |
| 5 | 重启后有未确认通知 | 通知仍在队列（可追溯），不被静默丢弃 |
| 6 | 已确认的通知 | 重启后不再出现 |
| 7 | 并发 32 线程各发 1 条，批量 200 条突发 | 每条恰好入队一次，无丢失、无串号（id/agent/message 各自对应） |
| 8 | 账本文件被改坏 / 未来 schema | 保留原文件、停写、不崩；内存账本仍可用 |
| 9 | 超大 / 非法 `id`（超长、控制字符、路径字符） | 拒绝并返回 400，不入队、不落盘 |
| 10 | 超过 CAP 的突发 | 有界，保留最近，淘汰最早的（不无界增长）；淘汰次数可读（`notify_evicted`） |
| 11 | 同一显式 id 带不同 payload | 首条保留，重复计数 +1 且冲突计数 +1，不另发 |
| 12 | 未知 agent / 任意正文与路径字段 | 落盘只有白名单字段；恢复显示静态中文摘要，正文与原始 id 不落盘 |
| 13 | 写盘失败（父路径非目录 / 账本被外部改坏） | 状态给出 `error`/`failures`，`savedGeneration` 不前进，不声称已保存 |
| 14 | 正文已被淘汰（超 64）的事件重放 | 仍判重（身份仍在 1024 窗口内）；`evicted` 不动、不多出一条；身份滑出窗口后同样投递才是新事件 |
