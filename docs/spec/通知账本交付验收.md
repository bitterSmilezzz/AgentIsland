# 通知入站账本：交付与验收

本次对应NOT-01的事件入队幂等、未确认提醒重启恢复和批量并发；需求出处及场景见[设计与验收规格](通知入站账本设计.md)。不代表NOT-01所有事件类型、通知中心历史或渠道送达已全部完成。

## 产品契约

- `/notify`和`/event`可携带稳定`id`，最长128字节、ASCII安全字符。按agent和规范事件类型分域，同身份重试只入队一次，首次正文保留；不同id同内容均入队。HTTP响应只表示受理，不表示持久化或送达。
- 无id时按内容与到达秒生成兜底指纹，同秒同文会抑制；该启发式无法区分同秒同文的两个新事件，可靠接入方应提供稳定id。身份窗口最多1024条，超出窗口不承诺永久去重。
- 恢复仅保留最近64条未确认提醒的安全摘要，不保存message/detail、任意agent名称、原始id、路径或私密会话正文。重启后提示正文未保存、查看来源；恢复不重新外发。确认后已成功保存的提醒不再复活。
- 写盘使用有界合并快照及独立线程，不在引擎锁内做文件IO。0600、原子写、schema/容量/revision校验；损坏/未来格式/外部修改保留原文件、停写并显示状态。
- 异常退出前尚未保存的新增提醒可能丢失、最近确认可能复活；HTTP受理不能当作耐久提交。正常退出走生产退出钩子在锁外限时等待保存，失败明确可见。
- 突发超过64条未确认时按有界策略淘汰最早，并显示淘汰数；“每条入队一次”不等于“无限保留不丢”。淘汰数由 `EngineState.notify_evicted` 提供（与 `notify_duplicates`/`notify_conflicts` 同风格），界面接线由 UI 侧负责；正文被淘汰而身份仍在 1024 窗口内时，重放仍判重。
- `agentisland notify` 每次调用都带一个新生成的稳定 `id`：该路径没有重试语义，不带 id 会让同一秒内两条相同消息的第二条被兜底判重丢掉，而 CLI 已印出「已投递」。请求体的类型键是 `/notify` 真正读的 `event`（`kind` 只属于深链路径），未知类型在本地按用法错拒绝，非 2xx 回应不再印成「已投递」。

## 仍未验 / 局限

- **未在真实 GUI 常驻进程内读取过 `notify_evicted` / `notify_restored` 的实际值**。
  上述数字来自真实进程探针与隔离测试；真实应用的长期值请在通知页查看。
  本轮核实过：本仓库**没有**不干扰用户的读取通道——HTTP 侧只有入站 `/notify`/`/event`，
  `agentisland state` 明确看不到 App 进程内自报，隔离实例又按设计关闭持久化。
  因此这一项只能由人工在通知页目视，agent 不为此做桌面探测（会触碰用户真实提醒）。
- 无 id 兜底只能区分「同秒同内容」；同秒两个独立事件会并成一条，可靠接入方须传稳定 id，
  这不是跨秒 exactly-once 承诺。
- 写盘前异常退出（强杀/断电）仍可能丢最近入队或复活最近 ack；正常退出（托盘退出、
  Cmd+Q、重启脚本的优雅退出）有 2 秒限时收尾，超时即放弃并记录。
- `notify_conflicts` 只在进程内存，重启后首条重新胜出、计数清零。
- 未做断电/强杀、磁盘满、跨平台实测；Windows 未验证。
- 来源事件→桌面提醒、外发入队→首次发出两段仍未测量。
