# 审查闭环口径（TASK-06）

> 回答一个问题：**「独立只读审查 → 修改后重审 → 作者≠审查者 → 结果不越权批准」
> 这条闭环在代码里的真实形状是什么？** 本文档把 TASK-06 的四个 token 逐一钉到
> 实现锚点上，由 `scripts/test-review-loop-contract.py` 逐条核对：指名的锚点
> 必须真实存在，禁止的事项必须真的没有。任何一侧漂了就变红。

## 环的形状（现状，全部有实现锚点）

闭环活在自动化管线（`scripts/automation/pipeline.py` 的 development 轮次）里：

| TASK-06 的要求 | 实现锚点 | 拒绝码 |
| :--- | :--- | :--- |
| **审查前门禁先绿** | 检查任一红 ⇒ 本轮不审（`blocked_by_checks`） | — |
| **独立只读审查** | 审查在一次性工作区跑：`readonly_source(review_wt, True)` 收权限 + 审查前后两次指纹对拍 | `review_source_modified`（审查写了源码即整轮拒绝） |
| **审查绑定被审内容** | `validate_review`：verdict ∈ {pass, revise, reject}、`input_digest`/`run_id`/`round` 必须对上本轮 | `review_binding_stale` 等 |
| **作者 ≠ 审查者** | 同一身份即拒 | `review_identity_invalid` |
| **修改后重审** | verdict=revise ⇒ 下一轮**重新走完整审查**（有界：`revision_limit_exhausted`） | — |
| **结果不越权批准** | verdict=pass 只产出 `local-only-candidate`（`publication: none`）；真正合并走 `publish.py merge`——先过 `candidate.verify` 全链（审查绑定/patch 逐字节/基线未漂）+ 目标 HEAD 恰为被审基线 + CI 报告绑定精确 SHA 且 success | 见 publish.py 的独立拒绝码矩阵 |

## 权限边界（审查结果能做什么、不能做什么）

- 审查 verdict **唯一**的作用是决定「进入候选 / 下一轮修改 / 拒绝」——它不是
  合并凭证。合并闸门（publish）从不禁用 candidate.verify：哪怕审查说 pass，
  证据链对不上照样拒绝。**审查与授权是两个独立闸门**，谁也不能替谁说话。
- 审查者对源码**只读**：写一个字都会被指纹对拍抓住并整轮拒绝（`mutate` 场景
  就是专门为这条钉的负例）。
- 审查在证据里**如实标注自己的种类**（`review_kind`，当前为
  `deterministic-mock`）：确定性回放不是独立意见，`independent_review` 如实为
  false；严格模式（`--require-independent-review`）下 mock 审查直接不够格。

## 显式边界（如实登记，不是缺口缝合）

- **「独立 AI 审查」的 AI 部分当前是确定性 mock**：真实审查 driver 与真实作者
  driver 走**同一条**可信授权策略硬门（`trusted_authorization_policy_unconfigured`
  ——调用方文本不是授权，凭据与策略验证器不存在之前不放行）。这是 ADR 0040
  的安全边界，不在决策前绕过；闭环的**机制**（只读、绑定、重审、双闸门）不因
  driver 是 mock 而变弱。
- 本口径只覆盖「审查闭环机制」；方案/代码审查的**内容质量**取决于 driver，
  不由本文件担保。

## 形状门禁核对什么

`scripts/test-review-loop-contract.py`：①四个 token 的锚点逐一存在（doc→code
绑定：指名标识符在代码里消失即红）；②禁止事项真的没有（publish 的 merge 路径
永远调用 candidate.verify，不存在「只凭审查 verdict 就合并」的旁路；审查指纹
对拍在，不存在无对拍的只读声明）；③本文档与门禁互相指认。
