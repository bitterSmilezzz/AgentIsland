# 入口能力矩阵（GW-09）

> 这张表回答一个问题：**同一个能力，在 GUI / CLI / TUI / Web 里能不能做到？**
> 它的用途不是好看，是让「某个入口缺某项能力」变成**可核对的**事实，而不是靠人记。
> 表里的每一格都由 `scripts/test-entry-capability-matrix.py` 逐条核对：
> 声称存在的必须能在代码里找到实现锚点；声称没有的必须真的没有。

## 矩阵

| 能力 | GUI | CLI | TUI | Web |
| :--- | :--- | :--- | :--- | :--- |
| 运行态快照 | 概览 / 智能体管理 | `status` `state` `doctor` | `top` | — |
| 用量与费用 | 用量分析 / 报表 | `tokens` `report` | — | — |
| 会话与任务 | 会话 / 任务 / 待办事项 | `open` | — | `POST /session` `DELETE /session` |
| 投递事件 | 远程通知 | `notify` | — | `POST /notify` `POST /event` |
| 模型与连接 | 模型与连接 | — | — | — |
| 进程排查与清理 | — | `check` `clean` | — | — |
| 设置与窗口 | 窗口排列 / 设置 | `open` | — | — |
| 构建自检 | — | `selftest` | — | — |
| 外部工具集成 | — | `raycast` | — | — |

## 口径

- **GUI**：桌面应用的工作台页面（`app/ui/js/navigation.js` 的 `workbenchPages`）。
- **CLI**：`agentisland <子命令>`（`app/src-tauri/src/cli.rs` 的 `COMMANDS` 表，标 `true` 的才算已实现）。
- **TUI**：`agentisland top`——持续观测看板。**它不接管终端**，所以是「看板上的一条线」而不是全屏 TUI；
  名字里带 TUI 会让人以为有全屏界面，这里按实际形态写。
- **Web**：本机 webhook 入口（`app/src-tauri/src/webhook.rs`），只监听回环地址。
  它是**投递**通道（外部把事件推进来），不是查询通道——所以矩阵里它没有「运行态快照」与「用量」。

## 为什么这样切分

- **写操作与读操作分开**：CLI 有 `clean`（终止进程）、GUI 没有——因为 GUI 侧是「看一眼就够」，
  而终止异常进程需要逐条点名孤儿；`clean` 的孤儿确认是 CLI 独有的谨慎。
- **本机才有���**：进程排查、清理、看板上都是**本机进程表**的事，Web 入口在别的机器上。
- **查询不外露**：Web 入口只接受投递与查询会话，不提供用量与状态查询——避免把本机状态变成
  一个可被任意本机进程读取的接口。

## 未覆盖（如实登记）

- 矩阵**只覆盖入口**维度，不覆盖「每项能力在各入口里的行为是否完全一致」
  （例如 `status --json` 与 GUI 概览的字段是否逐字对齐）——那需要逐项对拍，尚未做。
- TUI 只有 `top` 一项，其余能力它**没有**——不是「待补」，是这个形态的取舍。
