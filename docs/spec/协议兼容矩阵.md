# 协议兼容矩阵（GW-03）

> 回答一个问题：**四类模型协议（Chat / Responses / Messages / Gemini），
> 在流式/tools/reasoning/usage/cancel 五个能力上各自支持到什么程度？**
> 它的用途不是好看，是让「某个协议缺哪项能力」成为**可核对的事实**，
> 而不是每个协议适配器各写一套各说各话。
>
> 矩阵是**数据**（唯一声明处在 `app/src-tauri/src/gateway_protocol.rs`），
> 由 `scripts/test-protocol-matrix.py` 逐格核对：文档与代码必须逐格一致。

## 矩阵

| 协议 | 流式 | tools | reasoning | usage | cancel |
| :--- | :--- | :--- | :--- | :--- | :--- |
| Chat | 支持 | 支持 | **不支持** | 支持 | 支持 |
| Responses | 支持 | 支持 | 支持 | 支持 | 支持 |
| Messages | 支持 | 支持 | 支持 | 支持 | 支持 |
| Gemini | 支持 | 支持 | **未知** | 支持 | 支持 |

## 口径

- **不支持 ≠ 未知**。「不支持」是协议本身没有这个语义（Chat 没有推理内容字段），
  我们也不打算造一个；「未知」是**还没验过**——写「支持」会让调用方按支持去写
  代码然后静默失败，写「不支持」则是不诚实的断言。Gemini 的 reasoning 属后者。
- **未知不是可用**：`Support::usable()` 只对 `supported` 为真。
- **矩阵是唯一声明处**：界面按它显示「该协议支持什么」，转发层按它决定能不能
  走某条路径。两边各写一份必然漂——所以只有一处。
- **Codex 当前只能写 Responses**：`provider.rs` 的 `ensure_writable_protocol`
  明确拒绝旧 `chat` 档位（可读不可写）。这与本矩阵不冲突：矩阵说的是
  **协议形状**的能力，档位协议是**写入目标**的约束。

## 未覆盖（如实登记）

- 本矩阵只管「**形状上**支持什么」，不保证任何真实网关的端到端行为——那需要
  真实凭据与真实服务端（GW-01 边界）。
- 「16 协议方向」「tools 分片/并行/结果」「SSE 任意切片」「畸形/过深/超限」
  「取消/流中断」等细粒度场景尚未逐项落地（本轮只立矩阵这一层地基）。
