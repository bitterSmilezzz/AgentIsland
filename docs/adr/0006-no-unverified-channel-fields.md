# 外发通道只预置核实过的形状，其余交给用户模板

2026-09-21 做「远程通知」时的原始需求是"送到邮箱或 IM（微信 / QQ）"。可选通道里 ntfy 的形状能直接从官方文档核实（`POST https://<服务器>/<主题>`、`X-Title`、`X-Priority`、公开服务器单条 4096 字节上限）；而 Server酱 / PushPlus / 企业微信 / 钉钉 / 飞书这几家，当时的文档站是 JS 渲染壳、404 或超时——**拿不到正文就无法核实字段名**。

决定：三个通道里**只有 ntfy 做成预设**；其余一律走「自定义 HTTP 模板」，端点与字段由用户从自己那家的控制台粘贴，用 `{key}` / `{title}` / `{body}` 占位，且**请求体模板必填**。凭据（SendKey / token / webhook 里的 key / SMTP 授权码）只进 macOS 钥匙串，条目名由通道唯一决定（`remote.ntfy` / `remote.customHTTP` / `remote.smtpEmail`），**不做成可配字段**。默认外发内容只到"哪个 Agent + 什么状态"为止，命令内容、文件路径与消息原文需要用户显式勾选 `includeActionDetail`。

**为什么不预置——这个坑已经踩过一次**：早先版本在 `bodyTemplate` 留空时自带一套 `title` / `body` / `content` 字段名，那正是文档里写着"不预置"却自己编了的行为。后果不是发不出去，而是**发出去且界面显示「已送达」**：中转服务收到一个它不认的字段照样回 200，用户端什么也没收到，排查方向指向网络而不是字段名。改成用户模板后，出错面从"我们猜错且看不出来"变成"你粘的对不对，点『发送预览』当场能看到实际会离开本机的原文"。同理，钥匙串条目名一旦做成可配字段，就会出现"密钥存了但名字对不上"——界面全绿、每次发送都失败、日志里查不出线索。

**这条边界的隐含前提：先有掩码，再放字段**。自定义模板等于把密钥放进一个会被打印、被复制、会进设置页的字符串，而用户被明确告知"把控制台地址整段粘进来"——那串地址本身就带凭据。所以 `RemoteSecret.maskedURL` 必须覆盖：query 里的 `?token=` / `?key=` / `?access_token=`、`{key}` 占位、**主机名首段就是密钥**的形态（Server酱 的 `https://<32位SendKey>.send/…`，判据用首段长度 ≥20 而不是整段主机名长度，否则 `sctapi.ftqq.com` 这种正常域名也会被遮掉，预览就认不出在往哪发），以及**路径段里的长令牌**。新增通道时先加掩码规则，再放该家的字段。

**取舍**：新用户配微信的成本从"选一个预设"变成"去自家控制台复制地址并粘模板"，多几步且依赖帮助文案写清楚占位符。换来的是**不会替用户编造字段名**，且各家改版不需要跟发一版。若将来某家的端点与字段能稳定核实到正文（不是渲染壳），可以升级为预设——但预设必须同时带上那家的限流口径，否则自动重试会把用户推向撞上限：ntfy.sh 这类公开中转按条数限流，这也是 `failed.permanent` 存在的原因之一（见 `CONTEXT.md`「明确拒绝 vs 暂时失败」）。
