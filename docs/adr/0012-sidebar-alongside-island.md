## 背景

AgentIsland 的界面一直只有一种形态：贴在屏幕边沿的一块浮层（灵动岛）。它解决的问题是
**不打断注意力的被动感知**——用户在工作，岛的呼吸灯与微细条告诉你「有 Agent 在跑 / 有东西在等你」，
碰一下才展开。

这个形态有两个结构性上限：

1. **容量**：卡片宽 372、展开高 520。Token 分析、配置档位、待办这类「要读一段、要填几个字段」
   的界面装不进去。硬塞的结果是要么把岛撑成一块半个屏幕的板，要么把功能砍成阉割版。
2. **可达性**：它靠光标触碰与鼠标点击进入。键盘流只在展开之后成立，且没有「常驻可见」的选项——
   想一边看列表一边敲终端，没有地方放。

迁移到 Rust/Tauri 之后出现了一个岔路口：新形态的窗口要按哪种做的？

## 决定

**两种形态并存**，由 `shell_mode` 选择（`island` | `sidebar`），**默认 `island`**。

- 两个窗口**在启动时就都创建好**，切换只改显示哪一个。于是「反复切换留下多个窗口」
  这类事在设计上不成立，也不需要靠记得销毁窗口来避免。
- 切换入口：设置项 `shell_mode`，或启动参数 `--shell=sidebar` / `--shell=island`。
  启动参数**只影响这一次运行、不写回设置**（改设置去试形态，试完还得记得改回来，
  那是最容易留下脏状态的做法）。
- 侧边栏是新窗口（贴左或贴右、宽度可拉、宽度记忆），几何走独立的 `placement::sidebar_frame`——
  一整列与「浮在边沿的卡片」不是一回事，共用一套定位只会让两边都别扭。

## 各自适用面（写清楚是为了以后不被当成缺陷报上来）

| | 灵动岛 | 侧边栏 |
| :--- | :--- | :--- |
| 场景 | 工作时的被动感知：瞥一眼就知道有没有事 | 主动查看与操作：读列表、切档位、记待办 |
| 注意力 | 不打断。收起态只是一条 6pt 细条 | 会占掉一列屏幕，是「我决定要看它」 |
| 容量 | 小卡片：五态、当前动作、汇总数字、三级导航 | 一整列：列表 + 表单 + 详情 |
| 输入 | 光标触碰展开，之后可用键盘 | 常驻，键盘可达 |
| 贴边 | 四边皆可（ADR 0003） | 只有左右两档（上下没有意义） |

**因此：配置档位与待办只在侧边栏可达**。这是形态分工，不是缺陷——
但必须写进 [README 的侧边栏一节](../../README.md) 与本节，否则会被当成 bug 报上来
（工作台的「开放项 3」已经预见到这一点）。

## 为什么默认仍然是 `island`

1. **默认值要为老用户的习惯负责**。升级之后界面突然变成一整列窗口，是打断性的变化；
   而「多出一个可选项」不是。
2. **迁移尚未完成**。今天实际交付给用户的是 Swift 本体（只有灵动岛）；
   Rust 端的侧边栏还没有像素级实样核对。默认值换成 `sidebar` 会变成
   「默认形态是一个还没被看过一眼的界面」。
3. **新用户看不到侧边栏**是真的代价，且**已记在开放项里**：要不要给新用户做一次性迁移逻辑
   （或者首次启动问一句），等 Rust 端成为默认交付物之后再定。今天的答案是**不做**，
   并且在 README 里写明它能怎么打开。

## 后果

- **两套几何与样式**：`island.css` 的专属部分（notch / sliver / edge-top）只在灵动岛壳下生效，
  侧边栏的样式全部挂在 `.shell-sidebar` 下（由 `js/shell.js` 按窗口 URL 上的 `?shell=` 挂上）。
  两条壳不共用根容器，避免样式串味。
- **显示内容共用一份模型**：一行 Agent「显示什么、怎么措辞、什么颜色、没读到时写什么」
  只有一处（`agentRowModel`），两种形态各自排版。**排版可以不同，说法必须相同**——
  字段与文案的分叉没有任何编译器会拦，只能靠哨兵
  （`models.rs` 的跨文件字段哨兵与类别覆盖哨兵）。
- **切换必须能来回**：因为两个窗口都在，切换是幂等的；测试覆盖了形态解析与回落
  （认不出的值一律回 `island`）、侧边栏几何与宽度钳制。
- **`shell_mode` 认不出的值回落到 `island`**：拼错的形态不该让谁开不出界面。

## 没做的

- 「反复切换十次无窗口残留」只有设计上的保证（两个窗口只建一次），**没有真按十次**。
- 侧边栏的**像素级实样**没有核对过（本机截图需屏幕录制授权）。
- 新用户默认看侧边栏的迁移逻辑：**不做**，理由见上。
