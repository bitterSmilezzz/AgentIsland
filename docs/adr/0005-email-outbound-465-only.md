# 邮箱外发只走 465 隐式 TLS，代码里不留 STARTTLS 那条分支

2026-09-21 做「远程通知」时，邮箱是用户明确点名要的通道之一（"送到邮箱或微信"）。macOS 上没有能用的本地发信通道：Foundation 不含 SMTP 客户端，系统自带的 `/usr/sbin/sendmail` 在新版 macOS 上常常只是个壳，没配转发就静默丢弃，而我们**无法判断它到底发出去了没有**——那条路直接违反本仓的诚实原则，所以自己实现 SMTP。实现到端口这一步遇到分叉：465 是隐式 TLS（连上就握手），25/587 是 STARTTLS（先建明文 TCP，再原地升级为 TLS）。

决定：**只支持 465**，并且不留任何 STARTTLS 代码路径。`Network.framework` 不提供「在已建立的 TCP 连接上原地升级 TLS」的能力，而 STARTTLS 正是那个形态——要做得换掉整层传输实现，证书校验与握手时序都得自己保证。落地成三道口径，每道都做各自该做的事：`RemoteChannelKind.missingField` 在**配置层**就报"仅支持 465（隐式 TLS）；25/587 的 STARTTLS 不支持"，用户在设置页当场看到原因；`SMTPSocketConnection.connect()` 里 `guard implicitTLS` 再兜一道，防有人绕过配置层直接构造；`SMTPClient` 里根本没有第二条分支。

**为什么强调"不留分支"**：v0.0.100 一度保留了 STARTTLS 分支与它的假服务器测试，但那分支永远走不到——配置层已经拦掉了。留下的代价不是死代码本身，而是**它让"支持 STARTTLS"这件事在代码里看起来成立**：下一个人读到分支就会以为通，测试读到分支就会以为有覆盖（那条测试驱动的是假 IO，不碰真实升级能力）。已随 5181391 删净：`SMTPSessionIO` 协议里连 `upgradeTLS()` 这个需求都已移除，源码里剩下的 "STARTTLS" 字样全是说明性的（拒绝它的原因、设置页文案、类型注释），加一条反向断言——"465 会话里绝不能出现 STARTTLS 命令"。

**同一决定的另一半是证书策略**：`connect()` 刻意**不设** `sec_protocol_options_set_verify_block`。一旦设了就是**接管**信任评估，而回调里拿到的 `sec_trust_t` 非空并不代表证书可信（框架总会建一个），在回调里 `completion(true)` 等于对任意证书放行——授权码就会发给任意一台中间机器。默认路径下 Network.framework 已按连接域名做 SNI 与服务端证书校验，够用。想"支持自签证书邮箱"的人会在 `connect()` 的注释上撞到这条，那是有意的。

**何时重开**：出现真实需求时再做——比如某个只有 587 的企业自建 SMTP。成本是一整条新的传输实现（含原地升级与握手后的能力重协商），不是给现有分支加两行。别以"补齐协议"为理由重开：QQ 邮箱与 163 邮箱都提供 465，常见场景已经覆盖。
