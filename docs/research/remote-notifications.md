# 让通知跨出这台 Mac（调研）

> **状态（2026-09-21）：已实现并发布**（v0.0.100 起，见 [CHANGELOG](../../CHANGELOG.md) 与 README「远程通知」一节）。
> 本文保留作决策依据，两处结论已被实现推翻：**「邮箱排在后面 / 建议走邮件服务商 HTTP API」**已被
> 自建 SMTP 客户端取代（只支持 465 隐式 TLS，理由见 [ADR 0005](../adr/0005-email-outbound-465-only.md)）；
> 「先做 ntfy + 企业微信」实际做成了「ntfy 预设 + 各家走自定义 HTTP 模板」，因为企微/钉钉/飞书
> 的字段名当时核实不到（见 [ADR 0006](../adr/0006-no-unverified-channel-fields.md)）。
> 下面第五节「需要你决定的四件事」当时提的问题都已定案，答案在两份 ADR 与设置页里。

> 需求：上班时用 Windows 远程操控 Mac，任务完成后 Windows 端收不到任何提示。
> 希望把通知送到邮箱或 IM（微信 / QQ）。功能必须是**可选**的，能开关、能配置。
>
> 这份文档先解释「为什么现在收不到」和「有哪些路可走」，再给建议。**没有动手写实现代码**，
> 因为选哪条通道是产品决定，而且它会把数据送出这台机器。

## 一、心智模型：为什么远程桌面收不到通知

macOS 的通知**不是一个网络消息**，它是本机上另一个进程画在屏幕上的一块 UI：

```
AgentIsland ──「交给系统」──▶ 通知中心进程 (notificationcenterui)
                                    │
                                    └─ 画在 Mac 的屏幕上
```

远程桌面（Windows 的 RDP / Parsec / ToDesk / 向日葵…）传输的是**屏幕像素**，
不是通知事件。所以两种情况都会「收不到」：

1. 通知弹在 Mac 自己的屏幕上，而你没看 Mac 屏幕；
2. 更常见的坑——macOS 在**锁屏 / 显示器睡眠 / 专注模式**下会直接丢弃或静默横幅，
   远程会话里往往正是这些状态。

结论：**在 Mac 这一侧想办法「让弹窗穿过远程协议」是走不通的**（没有可挂钩的通道）。
唯一可靠的办法是让通知走网络到你的手机/另一台电脑，也就是「外发」。

## 二、可选通道盘点

按「要不要自己养一台服务器」分两类，这是最要紧的分界线。

### A 类：不需要自己的服务器（推荐起步）

| 通道 | 怎么工作 | 到手机 | 凭据形态 | 中文生态 | 备注 |
|---|---|---|---|---|---|
| **ntfy.sh** | 一个 HTTP POST 到 `https://ntfy.sh/<你起的随机主题>`，手机装 ntfy App 订阅该主题 | ✅ 原生推送 | 就是那个 URL（**URL 即密钥**） | 一般（要装 App） | 开源、可自建、免费额度够用；最像「零配置」 |
| **企业微信群机器人** | 群里加机器人 → 得到一个 webhook URL → POST 一段 JSON | ✅ 微信里收 | webhook URL（含 key） | ✅ 你已在企业微信生态 | 需要你是群主/管理员；有每分钟条数限制 |
| **钉钉自定义机器人** | 群设置里添加机器人 → webhook URL，**通常强制「加签」**（HMAC-SHA256 带时间戳） | ✅ | URL + `secret` | ✅ | 加签要在我们这边算 HMAC，实现稍多几行 |
| **飞书自定义机器人** | 同钉钉，群 → 添加自定义机器人 → webhook | ✅ | URL（可选签名） | ✅ | 与钉钉形态几乎一致 |
| **Server酱 / PushPlus（方糖系）** | 注册拿一个 sendkey，GET/POST `sctapi.ftqq.com/<key>.send?title=…` | ✅ 推到微信服务号 | sendkey | ✅ 专为中国用户做「发到微信」 | 免费版有每日条数上限；依赖第三方存活 |
| **邮件** | 见下方「为什么邮箱排在后面」 | ✅（手机邮箱） | SMTP 账号/授权码 | ✅ | 最「正式」，但实现最麻烦 |

### B 类：需要自己有一台公网服务器

自建 ntfy、Bark（iOS 专用）、Telegram Bot（在国内不可达）、Matrix、企业自建应用……
除非你已经有服务器，否则不建议从这类起步——它把「装个 App 就能收」变成「先运维一台机器」。

## 三、为什么邮箱排在后面（技术原因，不是偏好）

1. **macOS 没有能用的本地发信通道。** 发送邮件要走 SMTP 协议，而 Apple 的
   Foundation **不含 SMTP 客户端**（只有 URLSession 走 HTTP/HTTPS）。可选做法只有三条：
   - 调系统自带的 `/usr/sbin/sendmail`：新版 macOS 上它常常只是个壳，
     没配转发就静默丢弃，且我们无法判断「它到底发出去了没有」——**这违反本仓的诚实原则**；
   - 自己实现 SMTP + STARTTLS + 认证（约 300 行网络代码，还要处理证书与超时）；
   - 走**邮件服务商的 HTTP API**（如 Mailgun / Resend / 腾讯 SES）——这样就能复用
     URLSession，但它同样要你注册账号并交出 API key，成本不比 webhook 低，收益只是「发到邮箱」。
2. **QQ 邮箱的「授权码 SMTP」是国内最常见的做法**，但它正是 SMTP 路线，落到上面第 1 条。

所以：**如果目标只是「人不在 Mac 前也能被叫醒」，IM webhook 是投入产出比最高的一条；
邮箱值得做，但应该等通道抽象层已经存在时再加，而不是为它先写 SMTP。**

## 四、建议的实现形状（等你选完通道再动手）

```
AgentIsland 的事件（完成 / 等待确认 / 消耗告警）
        │
        ├─ 本地：UNUserNotificationCenter（现状不变）
        │
        └─ 外发（可选、默认关闭）
             RemoteNotifier ── 节流 / 去重 / 静默时段
                   │
                   └─ 一个协议：OutboundChannel { func send(text, priority) async -> Result }
                        ├─ WebhookChannel(kind: .ntfy | .wecom | .dingtalk | .feishu | .serverchan)
                        └─ （将来）EmailChannel(通过 HTTP API)
```

三条硬约束（这三条我认为不可谈判）：

1. **凭据只进 macOS 钥匙串。** 本仓的红线是「源码与配置文件零硬编码 secret」；
   而 webhook URL 本身就是 secret（拿到它的人就能给你发消息），所以它不能进
   `UserDefaults`（UserDefaults 是明文 plist 文件，会被备份、被同步、被 dump）。
   落地方式：`SecItem` 存 Keychain，设置页只做「录入 / 覆盖 / 删除」，界面上永远显示掩码。
2. **只发最小内容，且发之前给你看一眼。** 默认只发「哪个 Agent + 什么状态 + 多久之前」，
   **不带会话正文、不带文件路径、不带命令内容**（这些在你这台机器上很敏感——
   本会话的命令与路径就是例子）。设置页放一个「发送预览」按钮，把要发出去的原文显示出来。
3. **失败必须如实。** 网络发送会失败（超时、限流、URL 失效）。本仓已经因为这个原则
   修过好几处「把没做到印成做到了」（清理进程谎报成功、CLI 谎报投递成功）。
   所以外发失败要在岛内留一条可见的降级提示，而不是静默丢弃。

另外需要的设计细节：
- **节流**：一次任务可能连发 5 条完成事件；同一 Agent 同一状态在 N 秒内只发一次。
- **静默时段**：夜里/周末不发（可配）。
- **只在离开时发**：可选「仅当屏幕锁定或面板收起时才外发」，人在机器前就不打扰。
- **开关粒度**：按事件类型分别开关（完成 / 等待确认 / 消耗告警）。

## 五、需要你决定的四件事

1. **先做哪个通道？** 我的建议：**ntfy + 企业微信**（一个覆盖「装 App 收推送」，
   一个覆盖「就在微信里收」）；钉钉/飞书只是 JSON 结构不同，可以随后加，成本很小。
2. **要不要发到微信**（走 Server酱/PushPlus 这类服务号中转），还是只到企业微信群？
   前者更私密（一对一），后者需要你建一个群。
3. **邮箱要不要现在做？** 若必须要，我建议走「邮件服务商 HTTP API」而不是 SMTP，
   这样不引入网络协议代码；代价是你得注册一个服务商并给我 API key。
4. **允许外发哪些字段？** 默认「Agent 名 + 状态 + 时长」。要不要带上「最后一条动作」
   （例如「运行: swift build」）？带上更有用，但它会把命令内容送出这台机器。

选定后我按上面的协议形状实现，并配齐：钥匙串读写、发送预览、节流、失败可见、
以及不依赖真实网络的测试（假通道注入，断言「发了几条、发了什么、失败时怎么降级」）。

## 六、实现结果（v0.0.100）

第五节问的四件事，回答是「个人微信 + 邮箱必须搞，选一个我都可以配置，都是可选项」。
落成下面这样。

### 通道：三个里只有一个预设

设置 → 远程通知：总开关 + 单选通道。每个通道各自一份配置（`RemoteNotifyStore` 按通道键存 JSON），
切走再切回来字段还在。

| 通道 | 形态 | 依据 |
|---|---|---|
| ntfy | 预设：`POST https://<服务器>/<主题>`、`X-Title`、`X-Priority`（4/3） | 官方文档核实过；公开服务器单条 4096 字节 |
| 微信（Server酱 / PushPlus / WxPusher）、企微、钉钉、飞书 | 自定义模板：地址与请求体都由用户粘，密钥写 `{key}`、标题 `{title}`、正文 `{body}` | 那几家的文档当时取不到（JS 渲染 / 404 / 超时），**没核实的字段名不预置**；模板留空时也不自带一套字段名 |
| 邮箱 | SMTP 465 隐式 TLS | `Network.framework` 不支持在已建立的 TCP 上原地升级 TLS，25/587 的 STARTTLS 做不了；在配置层拦住并说明，而不是让用户配完发现每次都不通 |

### 凭据：钥匙串 + 四形态掩码

条目名由通道唯一决定（`remote.ntfy` / `remote.customHTTP` / `remote.smtpEmail`），不做成可配字段。
写入是「先 add，遇重复才 delete+add」。`RemoteSecret.maskedURL` 覆盖：
`?token=` / `?key=` / `?access_token=` / `?sendkey=`、`{key}` 占位、主机名首段是 20+ 位字母数字
（与大小写无关）、路径段里的 16+ 位长令牌。另两条独立警告：明文 `http://` 端点、
地址里没 `{key}` 却像含凭据（会明文进 UserDefaults 并显示在预览里）。

### 默认外发内容比原计划更少

原计划第四条问「要不要带上最后一条动作」，实现给的答案是：**默认不带，且时间也只在完成时给用时**。
「等待你确认」这类事件就在此刻发生，写成「3 分前」是谎报，所以显示「刚刚」。
命令与路径要显式勾选。**深链与 `/notify`、`/event` 产生的事件一律不外送**——
岛内能显示「外部投递 ·」前缀，手机上看不出，否则本机任意进程都能往用户手机灌文字。

### 节流、静默与「只在无人时发」

- 节流键是 `agentId + 事件类型`，且「查窗口 + 预登记」在一次加锁里完成；没发出去就回滚登记。
- 静默时段支持跨零点；写坏的时间窗**整段作废**（宁可多发也不全天吞掉），
  并且设置页会显式说「这一段时间窗无效，实际按不静默处理」——否则用户对着一个没生效的窗口毫不知情。
- `onlyWhenAway` 的判定在 v0.0.101 补了第三条信号。原来只认「屏幕锁定 + 显示器睡眠」，
  而**远程桌面连着 Mac 时这两条永远为 false**（实测本机：会话字典里没有 `CGSSessionScreenIsLocked`、
  `CGDisplayIsAsleep=false`，键盘 771 秒没动）——开关一开就等于永远不发，
  而这正是用户唯一在用的形态。现在加「无输入超过 N 秒」（默认 120s，
  `CGEventSource.secondsSinceLastEventType(.combinedSessionState)` 取键鼠里最近的一次），
  这是远程场景唯一有效的判据。取不到时长时 fail-open 按「已离开」发，
  设置页实时显示当前判定与三条信号，让「有没有生效」当场看得见。
  已知盲区：`ScreenPresence.idleSeconds` 要真实 GUI 会话，测试造不出来
  （变异验证里「让它永远返回 nil」0 红），所以靠页面自证，不假装测过。

### 实测与复核抓出的缺陷（离线测试全绿的条件下）

本地起了一个假接收端（`127.0.0.1:8099`）与一个自签证书 TLS 服务器，把真实 URLSession /
`NWConnection` 链路走通，加上两轮代码复核，共 9 项（另有 5 处「变异未被捕获」暴露的是测试本身没覆盖）。逐条与修法见 `CHANGELOG.md` v0.0.100，
其中最值得记住的三类：

1. **协议层的静默丢字**：HTTP 头值必须 ASCII，URLSession 直接丢掉非 ASCII 且不报错，
   本地还报 `.delivered`。同一套编码不能既当头值编码器又当查询串编码器（头值允许 `& # % +`）。
2. **异步状态机的「没有下一次回调」**：`NWConnection` 对被拒绝的连接停在 `.waiting` 自行重试，
   只在状态回调里恢复续体会永久挂住；读路径的 deadline 放在回调里比较同样是永久挂住。
   这类 bug 的特征是「按钮永远转圈 + 泄漏一个持有明文凭据的任务」，必须用真 socket 测。
3. **闸门漏在构造侧**：`/notify` 忘了打 `externallyDelivered` 标记，
   于是消费侧再严格的判断也接到了一个"看起来是引擎自己判定"的事件。
   防伪造的标记要在**产生事件的那一处**就写上，结构断言也得钉在那一处。

### 仍未做（诚实清单）

- 端到端只验到「本地假接收端收到什么」与「证书不被信任时连不上、且连不上会如实返回」。
  真实 ntfy.sh / 微信中转 / QQ 邮箱需要用户自己的凭据，本仓不代持，
  也就**不替用户宣称「已收到推送」**——这一步只能由用户按「发送测试」完成。
- 未做多收件人、附件、HTML 邮件；SMTP 只做「发一封纯文本信」的最小集合。
- 未做「按网络/热点判断在不在公司」这类自动策略。
