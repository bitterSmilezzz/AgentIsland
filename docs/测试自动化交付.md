# 测试自动化建设与统一验收

状态：实施中。2026-10-15，基线 HEAD `61d3fa3fa08e306eb2f8a187494e21addb1b31d1` 加当前工作树；未提交、未发布。

## 本轮范围

统一统筹既有 agent 的产出，复用已有测试资产，形成可信执行入口、自动触发、可下载报告和负例守护。Rust/资源诊断/用量归并/通知持久化均纳入集成验证，文档及未实现需求保持诚实状态。

## 执行约定

- 选中检查全部通过才返回 0；失败返回 1，配置错误 2，缺环境未执行 3。`blocked` 单列但不能把整轮标为通过。
- 自动集合只使用合成数据。真实 VM、受控客户端、私有会话探针分开；私有探针一次显式选择一个，不批跑全部 ignored。
- 测试失败不自动重跑到绿；原始失败保留。子进程超时回收、独立项继续汇总；日志不录入原始会话与敏感输出。
- 每次报告绑定 run ID、实际被测源内容摘要、需求/清单版本。测试中源发生变化则拒绝声明通过。
- 自动开发的验证目标必须是该轮隔离产出；工作区只清理本轮创建且干净的目录，脏产出保留。
- CI 和发布脚本共用 `pipeline.py --profile ci`。本轮仅编辑触发配置，不执行远程提交/发布、不安装本机定时任务。

### 第三轮：开发闭环与解释器前提（同日续）

- **独立审查闭环。** 开发链路从「agent → checks」扩到「当前源码快照 → checks → 独立审查 →
  有界修订重验 → 本地候选」。作者与审查者身份必须不同；审查在新 revision 的只读工作区；
  结构化结果含 `verdict`/`input_digest`，`statusOK` 不构成批准；修订后检查与审查一起失效。
- **`--preauth` 不再是权限。** 任意字符串不再放行真实驱动；未配置可信授权策略时明确
  `blocked: trusted_authorization_policy_unconfigured`，不建工作区、不调真实 agent。
- **解释器下限（本轮新发现）。** 系统 `python3` 是 3.9，而构建收据工具需要 3.11+（`tomllib`），
  CI 却固定 3.12——同一门禁在本机崩溃、在 CI 通过，本机的崩溃还会被读成「被测代码坏了」。
  现在 `requires_python` 声明下限，执行器**自行解析**满足下限的解释器（不信任 PATH 顺序），
  找不到则记 `required_python_missing:<版本>`（blocked，不是 failed）。`build-app.sh` 经
  `scripts/common.sh` 的 `PYTHON_MIN` 使用同一解释器。
- **驱动加固。** 非零退出不再能被 `status:"OK"` 洗白；超时/上限/中断都清理进程组；
  失败结果不带原始输出；`command` 固定脱敏。
- **构建收据。** 全量构建输入内容摘要（325 文件）绑定产物哈希，mtime 不能替代；
  构建前后源码漂移拒绝出收据。
- **输入与扫描边界。** GitHub 触发器只读一次 issue、正文标为不可信材料、有界；
  扫描器中间产物改私有目录，并发不互串。
- **receiver 加固。** 到期/取消/撤销在取锁后与 ACK 前复核；ACK 写出即提交；
  guard panic 不再绕过清理；`stop()` 返回结果，runtime 在未确认清空时报 `uncertain`
  而不是宣称「临时正文已清空」。

### 第四轮：解释器前提、扫描器隔离与证据链（同日续）

- **`test-automation-artifact.py` 自身的解释器下限。** 门禁会挑满足下限的解释器跑它，
  但它自己用裸 `python3` 加载 `artifact.py`，于是门禁选 3.14、它却以 3.9 拉 `tomllib` 崩溃。
  现在脚本入口自带版本检查，不够则 rc=3 与明确原因，而不是裸 traceback 被读成"被测代码坏了"。
- **仓库 sentinel 抓出外部候选的真实缺陷。** `test-scan-secrets.sh:153` 在 `set -u` 下展开
  未定义 `$RUN_TMP`。`shell_quoting_sentinel` 把它挡下来了——这正是该 sentinel 存在的理由。
  修复后 sentinel 41/41、扫描器套件 33/33 两侧皆绿。
- **扫描器中间产物隔离。** 原来固定写 `/tmp/scan-secrets-*.txt`，并发扫描会互相覆盖命中、
  互相清文件；测试还会 `rm -f /tmp/scan-secrets-*`（可能删掉别人的）。改为每 run 私有
  `mktemp -d`(0700)，清理只清本轮登记的文件。规则、棘轮、打码、零命中类别均未放宽。
- **证据链落进 run.json。** `provenance`（宿主、工具版本、需求/矩阵/清单摘要）与
  `requirement_results`（36 个需求逐条执行状态）现在随每轮报告落盘。实测本轮：
  `mapped_checks_passed` 16 / `partial_execution` 4 / `unimplemented` 16，
  `complete_requirement_verified` **全部为 False**——已映射检查通过不等于需求完整覆盖。
- **`release` profile 已登记**（ci + 两项随包 CLI 校验）。

正好违反"失败不能丢记录"这条核心不变量。

- 新增 `_atomic_json_unanchored`：独占创建 + 原子替换，**明确较弱**（不拒绝符号链接父目录）。
  它存在的唯一理由是"记录写不出来比保证较弱更糟"。
- `_append_log` 在无锚定能力时走同类回退，并返回 `log_written_unanchored`，不冒充强保证。
- 记录新增 `write_guarantee` 字段自报级别（`anchored_dir_fd` 或 `unanchored_no_symlink_refusal`），
  读者不会误以为本机提供了它没有的符号链接保护。
- 回归：模拟 `_anchored()=False`，暂停记录仍写成功、`run_id` 正确、保证级别如实标注；
  锚定主机上标注强保证。pause 22/22。

**第二十一轮：门禁判别力盘点——给红线门禁补上反向证明（2026-10-16）**

registry 有 `discriminating_by` 这个机制：声明一条"破坏实验"命令，在隔离副本里注入缺陷，
证明门禁**能失败**而不只是总能通过。但 **71 个 check 里只有 2 个用上**（`automation.artifact`、
`automation.snapshot`）。本轮从最重要的一个开始：`secrets.workspace`（`scan-secrets.sh`），
它是唯一把凭据挡在 git 之外的门禁——它若不能失败，整套安全承诺就是空的。

**它确实能失败（4/4）**，四种形状各自注入隔离副本：AWS access key、私钥块、
GitHub PAT、Slack token，全部 rc=1。但这条证据此前只在一次性脚本里，**没有回归保护**——
今后任何人改扫描模式，都不会有人知道它是否还能抓住凭据。已按 `test-scan-secrets.sh`
既有的 `fixture`/`check` 范式补成 4 条回归。

**过程中踩到三个坑，都已纠正，且每个都是有价值的发现：**

1. **写死的凭据字面量会被编辑层脱敏改写。** 第一版把完整的私钥块头直接写进脚本，
   落盘变成占位符，于是"扫描器没抓住"——是夹具错，不是产品错。改为**运行时拼接**：
   `printf -- '-----BEGIN %sPRIVATE KEY-----' 'OPENSSH '`。（本条说明文字本身也必须
   拆开写：完整的块头形状会让 `snapshot_safety` 的硬规则把整份文档当凭据拒掉——
   本轮第一版文档就是这么把 `automation.break-artifact` 连带弄失败的。）
2. **断言不能要求扫描器回显命中原文。** `scan-secrets.sh:94` 的 `redact()` 刻意打码
   （`«masked»`），这是红线：密钥不得进终端或 CI 日志。所以任何凭据形状都不可能出现在
   输出里。改用 `:193` 打印的**规则名**（`    [<rule>] <file> → <masked>`），规则名是明文。
3. **第一版断言太弱，是空断言。** 只断言"有未备案命中"时，把 `cred_prefix` 规则整个打瞎，
   3 条仍然 OK——因为 `username`/`email` 等通用规则也让扫描器非零退出。**收紧到具体规则名后
   反向证明成立**：打瞎 `cred_prefix` → AWS/PAT/Slack 三条立刻 FAIL，`private_key` 仍 OK
   （它走独立规则，符合预期）。

| 证据 | 结果 |
| --- | --- |
| 四种凭据形状注入隔离副本 | **4/4 rc=1**（扫描器能失败） |
| `test-scan-secrets.sh` 全量 | **37 OK / 0 FAIL**，rc=0 |
| 反向证明：打瞎 `cred_prefix` | AWS / PAT / Slack **FAIL**，`private_key` 仍 OK |
| 还原后 `scan-secrets.sh` | 与 sabotage 前**逐字节一致**（shasum 相同），未被削弱 |

**仍未做**：其余 67 个 check 的判别力实证。`discriminating_by` 的机制完备（含 host 门、
指纹绑定、外部授权阻断、输出上限），缺的是覆盖面；逐个补是长期工作，本轮只证明了
**方法论可行且已在一个最重要的门禁上落地**。

**本轮还暴露了一个此前不知道的耦合，而且是我自己的改动引发的**：把凭据形状写进
`docs/测试自动化交付.md` 的说明文字后，`snapshot_safety.py:184` 的**硬规则**把整份文档
当作凭据，于是依赖源码快照的 `automation.break-artifact` 与 `automation.break-snapshot`
**连带失败**（`verify-framework.sh` 从 ALL VERIFIED 变成 rc=1）。这与上面第 1 条是同一件事
的另一面：**在这套框架里，连"描述一个凭据长什么样"都会触发凭据门禁**。修正方式是文档里
也必须拆开写形状；修好后两个 break 实验恢复 `ok=True`，全量门禁回到 ALL VERIFIED。

这条耦合值得记住：任何新增的判别力测试只要内含凭据形状，就必须同时检查
`snapshot_safety` 的硬规则与 `scan-secrets.sh` 的绝对零命中规则——否则会在 `--isolated`
路径上炸开，而那个失败点离改动位置很远，极难归因。

**第二十二轮：判别力无法靠静态扫描分类——一个负结果（2026-10-16）**

第二十一轮只补了 1 个 check，还剩 68 个。本轮想先"系统分类"，再决定补哪些，
**结论是这个思路不成立，负结果本身有记录价值。**

写了三个递进的分类器，全部不可信：

| 版本 | 判据 | 报出的"缺口"数 | 为什么错 |
| --- | --- | --- | --- |
| 1 | `assert(Equal|True|...)` 等具名断言 | **40** | 漏掉 `assert.deepEqual`、`assert.ok`、`assert.match`——整个 JS 测试都被误判 |
| 2 | 任何 `assert.<name>(` | 12 | 漏掉 Python 的**语句式** `assert expr == y`（`test-version.py` 全中招） |
| 3 | 加上语句式与 shell 的 `check` helper | 19 | 修好了 assert，但 `INJECT` 收紧后把大量正常 check 挤进缺口 |

**决定性反例**：`auto01.version` 的 `scripts/test-version.py` 是教科书级的判别力测试——
五处独立发布输入（`Cargo.toml`/`Cargo.lock`/`tauri.conf.json`/`CHANGELOG.md`/`README.md`）
**各自单独漂移**，逐一断言必须被拒，外加一个非法版本。三个分类器分别把它判成
缺口、缺口、缺口。**实证它反而一次就过**：把 `check-version.py:21` 的
`raise SystemExit(...)` 改成 `pass`，测试立刻失败并指名
`app/src-tauri/Cargo.toml drift was accepted`；还原后通过。所以它不是缺口，
是分类器错了。

**方法论结论**：判别力只能**实证**（注入缺陷 → 看门禁是否拒绝 → 还原），
不能**静态推断**。原因是"有判别力"不是源码形状的属性：同一份 `assert` 在
一个测试里守护真实契约，在另一个里只是守护一个常量；同一个 `inject` 字样
可能出现在注释里。正则看到的是词，不是语义。

**因此放弃批量分类，改为按价值逐个实证。** 已实证的两个：

| check | 判别力实证 | 反向证明 |
| --- | --- | --- |
| `secrets.workspace` | 4/4 凭据形状被拒 | 打瞎 `cred_prefix` → 3 条 FAIL |
| `auto01.version` | 5 处独立漂移 + 非法版本均被拒 | 打瞎漂移检测 → 指名 `Cargo.toml drift was accepted` |

两者都不需要 `discriminating_by` 声明——它们的测试本身就是破坏实验，加声明是重复劳动。
`discriminating_by` 的正确定位是：**给那些测试自身不含负路径的门禁补一道**，
而不是给全部 71 个 check 盖章。本轮未改任何产品文件（`check-version.py` 还原后
与原件逐字节一致）。

**第二十三轮：执行时间基线与一处过期登记（2026-10-16）**

此前所有轮次都在修正确性，**从没有人验证过执行时间**——而一个慢到没人愿意跑的门禁
等于没有门禁。本轮取真实基线，并核实超时余量。

**ci profile 实测总耗时 230.3 秒（63 个 check）**，最慢的十个：

| check | 耗时 |
| --- | --- |
| `rust.default` | 34.4s |
| `automation.development` | 32.4s |
| `task01.detailnav` | 26.5s |
| `automation.verifier` | 23.7s |
| `automation.runner` | 23.4s |
| `automation.driver` | 18.8s |
| `automation.adapters` | 12.3s |
| `automation.trigger` | 5.8s |
| `automation.selfcheck` | 5.1s |
| `sec01.scansecrets` | 5.0s |

**超时余量充足，无误杀风险**：71 个 check **没有一个**单独声明 `timeout_seconds`，
全部走默认值（CLI 默认 900s，CI 传 1800s）。最慢的 check 实际 34.4s，
余量约 **26～52 倍**。`pipeline.py:1280` 的有效预算是 `max(CLI 值, registry 声明值)`，
所以声明只会放宽、不会偷偷收紧——这个方向是对的。

**发现一处过期登记并已修正**：`rust.default` 的 `source` 写着"976 个 `#[test]`，
2026-10-15 统计"，而实测是 **1020 passed / 14 ignored**。这是框架里唯一描述测试规模的

零命中）——纯人工维护的注释，已经过期。若某天测试数**暴跌**（例如被误删），`cargo test`
照样退出 0，框架不会发现。

**但没有为此建"测试数棘轮"，因为静态计数不可复现**：源码里 `#[test]` 字面量 1037 处，
扣掉紧跟 `#[ignore]` 的 14 处得 1023，与实测 1020 仍差 3；原因是 **41 处 `#[test]`
受 `cfg(not(...))`/`unix`/`windows`/`target_os = "macos"` 等条件影响**，静态扫描无法判定
它们在当前平台是否参与编译。任何"静态计数 == 登记值"的断言都会误报。
已改为登记**实测数**并在同一条 `source` 里注明为何不用静态计数，让下一个读者
不必重新发现这件事。

**本机全绿与干净检出可用是两件事**：`.build/` 在本机一直存在，所以这个错误
在本地永远看不见。
