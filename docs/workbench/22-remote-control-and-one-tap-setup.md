# 22 · 远程操控与一键全配

> 用户在手机上（DimRemote）口头提出的需求，本文把它落成口径与方案。
> 只写判断与事实，不排期（排期并入 10 号 Phase）。所有现状经 2026-09-26 核对源码。

## 0. 用户要什么（原话整理）

1. **手机上远程访问这台电脑的 AgentIsland，并在手机上真实操作**——不只是看。
2. **手机上加一个「红糖」**：常驻的助手形象。
3. **一键全配**：新模型/新账号来了，**一次配好**。「每个人都要配很麻烦」。
4. **能自动就自动，能省就省**，尽量人性化——把需要手动配置的尽量一次解决。
5. **除了手机 app，还要能接 QQ 机器人、微信机器人**。

## 1. 用户拍板（2026-09-26）

- **远程控制权限：也能下发任务和写代码**（不是只读）。
- **优先级：先做「一键全配 + 自动连上」，红糖随后。**

第 1 条我(agent)执行，但**有一条不让步并在此声明**：**未经鉴权的远程执行等于把这台电脑的 shell 交出去。**
所以「配对码鉴权」是硬前置，不是可选装饰。用户在手机上选了这个授权范围，
我就必须把授权做实——否则等于替他做了一个他不知道自己同意的决定。
（理由：手机可能丢、局域网可能被别人连上、QQ/微信 bot 的端点天生暴露在公网服务上。）

## 2. 一个必须现在定的架构方向：入站控制层与通道解耦

**今天的外发是单向出站**（`RemoteNotification.swift:61-63`：ntfy / customHTTP / smtpEmail），
只能「电脑喊你」。用户要的是**入站控制**——「你在手机上操作电脑」。这是两件不同的东西，
不能靠给外发通道加个回程糊出来。

**决定**：远程做成**两层**。

```
上层：通道适配器（可增删）        下层：入站控制面（一套，带鉴权）
  手机 app（我们自己出）              GET  /state        读实时状态
  QQ bot                              POST /command      执行管理动作
  微信 bot                             POST /exec         下发任务（用户已授权）
  （将来 Telegram/飞书…）              POST /pair         配对，一次配好
```

**好处正是用户第 4 条要的**：加第四个通道只是加一个适配器，不是重做一遍。
此前调研过的 DeepChat（[11 号](11-deepchat-another-route.md):40）就做了五个 IM 通道，
证明这条路可行；但它因此被我们判为「另一条路线」——**从监控工具变成了 agent 的前端**。
我们要守住不当 agent 前端的界：bot 侧可以下发任务，但**不承接「在 IM 里写代码」的完整 IDE 化交互**。

## 3. 地基比预期好：鉴权不必从零造

这是本轮最重要的发现，直接决定第 3、4 条能不能「省」。

`Sources/AgentIsland/LocalEventServer.swift` 早就有：

- **`engine.selfReportTokens`**（`:43-51`）——一份「可信自报令牌」，接入方凭它证明自己是可信的；
- **macOS 14+ 已限定回环监听**（`:63-65`，`requiredLocalEndpoint = .hostPort(host: .ipv4(.loopback))`）；
- **macOS < 14 的暴露面被显式告警而非假装安全**（`:67-68`，原注释就写着「`/notify` 无鉴权」）。

**所以「一键全配」可以复用这套令牌，不必新造一套凭据系统**：

| 步骤 | 做法 | 为什么省 |
|---|---|---|
| 电脑侧 | 启动时生成配对码（复用 `selfReportTokens` 的 store，`:41` 注释已写明「两处各开句柄就会有那天」） | 不加第二份凭据存储 |
| 手机侧 | 输一次配对码 → 拿到令牌 → 存本地 | 用户只输一次，之后自动连 |
| 新设备 | 同一步 | 又一个人来只输一次配对码 |
| bot 侧 | 令牌即 bot 的凭据 | 同一套，不另发 |

**这正是「一次配好、能省就省」的落点**：不是把配置项减少，而是**把「可信关系」变成一次性配对**，
此后新模型/新账号只需在电脑侧加档位（Phase 2 的档位卡），手机自动可见，无需再配一次。

## 4. 「红糖」是什么（先定边界，避免做偏）

用户说的是手机上常驻的助手形象。**现在只定三条边界，不做设计**：

- 它不是 agent、不是第二个对话模型——我们的定位是不当 agent（[21 号 §1](21-product-positioning.md)）。
  它是**已有的五态与 token 数据的人格化出口**：agent 卡住了它提醒你、token 超预算它喊停。
- 它读的东西必须是**同一份 `AgentObservability` 口径**，不能自造一套说辞——
  否则出现「红糖说在跑、卡片说空闲」，那正好击穿我们唯一的外部可验证差异（三个出口一致）。
- 形象与动效遵循「克制是默认项」（20 号判断 3 + `docs/research/ui/` 共识 1），
  不常驻动画、不抢通知。

## 5. 手机 app 自己出，不走 DimRemote（用户 2026-09-26 拍板）

**DimRemote 要订阅，用户明确不用，要自己的。** 所以「自动连上」不依赖任何第三方 app，
而是自己出 app + 自己出 bot。代价由用户接受，我也就不再去找 DimRemote 的复用点位。

**这条决定顺带把架构逼到唯一解**：一个自家的手机 app 要能连上家里的电脑，
必须有**公网可达的接入点或中继**，而这与该 app 用哪个服务实现无关。见第 6 节。

## 6. QQ bot 两种模式的实测结论（2026-09-26 核过官方文档）

[QQ 机器人官方文档](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/interface-framework/event-emit.html)
明确给两条路，**成本差一个量级**：

| | WebSocket 长连接（推荐） | Webhook 回调 |
|---|---|---|
| 方向 | **出站**（我们连出去） | 入站（QQ 推进来） |
| 公网 IP / 域名 | **不需要** | 必须 |
| 端口 | 无 | 只能 80 / 443 / 8080 / 8443 |
| 鉴权 | OpCode 2 Identify 带 `token` + `intents` + `shard`，连上即得 session | ed25519 签名校验（`plain_token` + `event_ts` 用 seed 派生私钥） |
| 连接维护 | OpCode 10 Hello 下跳周期（文档示例 45000ms）、OpCode 1 心跳、OpCode 11 ACK、OpCode 6 Resume、OpCode 7 重连 | 平台重推 |

**结论：走 WebSocket 出站。** 理由与用户「能省就省」直接一致——它**不需要公网 IP、
不需要域名、不需要端口映射、不需要反向代理**，家里电脑直连即可。第三方实现的原话即
「通过 WebSocket 连接 QQ 平台（出站连接，无需公网 IP）」，官方文档的 WebSocket 一节
（OpCode 10 Hello → OpCode 2 Identify → 心跳）也确认了这一条路径。

**这与第 2 节的入站控制面不矛盾，反而互补**：QQ bot 这一路是**出站**（连到 QQ），
因此天然不暴露本机监听面；真正需要鉴权硬闸门的是**手机 app 那一路的入站控制面**
（`POST /command` / `POST /exec`）——它才是要接到公网的那一侧。两者都要鉴权，但威胁模型不同。

## 7. 手机 app 那一路的公网问题（必须做的选择）

自家 app 要远程连上家里的电脑，绕不开三种形态：

| 形态 | 成本 | 代价 |
|---|---|---|
| **A 直连（Tailscale/组网）** | 中：用户装一个组网客户端 | 需引导用户装额外软件，但**零服务器成本、零运维**，且凭据不出本机 |
| **B 自建中继** | 高 | 要一台服务器 + 域名 + 证书 + 运维；流量经我们的手 |
| **C 走既有云函数/对象存储** | 低 | [08 号](08-chendahuang-cloudflare-research.md) 已研究过「只借思想不上云」，与 C 冲突 |

**我(agent)推荐 A（组网）**：它最符合「不碰网络、不持有凭据」的既有口径
（[ADR 0009](../adr/0009-credential-boundary-borrow-dont-hold.md)）——组网后手机与电脑仍是点对点，
我们只做配对，不做中转，也不存任何 token。B 会让产品性质从「本机工具」变成「有后端的服务」，
那是另一个量级的事。

**这一步需要用户确认**，因为它决定要不要买域名与服务器。

## 8. 还需要用户拍的（原 5.3 仍在）

**`POST /exec` 的边界**：用户已授权「也能下发任务和写代码」，但「能跑任意 shell」与
「只能跑预定义管理动作」是两个量级的风险面。我(agent)倾向**白名单 + 明确的一次性授权提示**，
但最终由你(用户)定——因为这是把 shell 交出去的范围。
