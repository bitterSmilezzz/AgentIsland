# 22 · 远程操控与一键全配

> 用户在手机上（DimRemote）口头提出的需求，本文把它落成口径与方案。
> 只写判断与事实，不排期（排期并入 10 号 Phase）。所有现状经 2026-09-26 核对源码。

## 0. 用户要什么（原话整理）

1. **手机上远程访问这台电脑的 AgentIsland，并在手机上真实操作**——不只是看。
2. **手机上加一个「红糖」**：常驻的助手形象。
3. **一键全配**：新模型/新账号来了，**一次配好**。「每个人都要配很麻烦」。
4. **能自动就自动，能省就省**，尽量人性化——把需要手动配置的尽量一次解决。
5. **除了手机 app，还要能接 QQ 机器人、微信机器人**。

## 1. 用户拍板（2026-09-26，共四条）

- **远程控制权限：也能下发任务和写代码**（不是只读）。
- **优先级：先做「一键全配 + 自动连上」，红糖随后。**
- **手机 app 自己出，不用 DimRemote**（它要订阅）。
- **公网接入走自建中继**（第 7 节：我记录了不同意见，但按用户的决定写方案）。
- **执行权限：白名单默认 + 电脑侧当面解锁后可任意**（第 8 节）。

第 1 条我(agent)执行，但**有一条不让步并在此声明**：**未经鉴权的远程执行等于把这台电脑的 shell 交出去。**
所以「配对码鉴权」是硬前置，不是可选装饰。用户在手机上选了这个授权范围，
我就必须把授权做实——否则等于替他做了一个他不知道自己同意的决定。
（理由：手机可能丢、局域网可能被别人连上、QQ/微信 bot 的端点天生暴露在公网服务上。）

## 2. 一个必须现在定的架构方向：入站控制层与通道解耦

**今天的外发是单向出站**（`RemoteNotification.swift:61-63`：ntfy / customHTTP / smtpEmail），
只能「电脑喊你」。用户要的是**入站控制**——「你在手机上操作电脑」。这是两件不同的东西，
不能靠给外发通道加个回程糊出来。

**决定**：远程做成**两层**。

```
上层：通道适配器（可增删）        下层：入站控制面（一套，带鉴权）
  手机 app（我们自己出）              GET  /state        读实时状态
  QQ bot                              POST /command      执行管理动作
  微信 bot                             POST /exec         下发任务（用户已授权）
  （将来 Telegram/飞书…）              POST /pair         配对，一次配好
```

**好处正是用户第 4 条要的**：加第四个通道只是加一个适配器，不是重做一遍。
此前调研过的 DeepChat（[11 号](11-deepchat-another-route.md):40）就做了五个 IM 通道，
证明这条路可行；但它因此被我们判为「另一条路线」——**从监控工具变成了 agent 的前端**。
我们要守住不当 agent 前端的界：bot 侧可以下发任务，但**不承接「在 IM 里写代码」的完整 IDE 化交互**。

## 3. 地基比预期好：鉴权不必从零造

这是本轮最重要的发现，直接决定第 3、4 条能不能「省」。

`Sources/AgentIsland/LocalEventServer.swift` 早就有：

- **`engine.selfReportTokens`**（`:43-51`）——一份「可信自报令牌」，接入方凭它证明自己是可信的；
- **macOS 14+ 已限定回环监听**（`:63-65`，`requiredLocalEndpoint = .hostPort(host: .ipv4(.loopback))`）；
- **macOS < 14 的暴露面被显式告警而非假装安全**（`:67-68`，原注释就写着「`/notify` 无鉴权」）。

**所以「一键全配」可以复用这套令牌，不必新造一套凭据系统**：

| 步骤 | 做法 | 为什么省 |
|---|---|---|
| 电脑侧 | 启动时生成配对码（复用 `selfReportTokens` 的 store，`:41` 注释已写明「两处各开句柄就会有那天」） | 不加第二份凭据存储 |
| 手机侧 | 输一次配对码 → 拿到令牌 → 存本地 | 用户只输一次，之后自动连 |
| 新设备 | 同一步 | 又一个人来只输一次配对码 |
| bot 侧 | 令牌即 bot 的凭据 | 同一套，不另发 |

**这正是「一次配好、能省就省」的落点**：不是把配置项减少，而是**把「可信关系」变成一次性配对**，
此后新模型/新账号只需在电脑侧加档位（Phase 2 的档位卡），手机自动可见，无需再配一次。

## 4. 「红糖」是什么（先定边界，避免做偏）

用户说的是手机上常驻的助手形象。**现在只定三条边界，不做设计**：

- 它不是 agent、不是第二个对话模型——我们的定位是不当 agent（[21 号 §1](21-product-positioning.md)）。
  它是**已有的五态与 token 数据的人格化出口**：agent 卡住了它提醒你、token 超预算它喊停。
- 它读的东西必须是**同一份 `AgentObservability` 口径**，不能自造一套说辞——
  否则出现「红糖说在跑、卡片说空闲」，那正好击穿我们唯一的外部可验证差异（三个出口一致）。
- 形象与动效遵循「克制是默认项」（20 号判断 3 + `docs/research/ui/` 共识 1），
  不常驻动画、不抢通知。

## 5. 手机 app 自己出，不走 DimRemote（用户 2026-09-26 拍板）

**DimRemote 要订阅，用户明确不用，要自己的。** 所以「自动连上」不依赖任何第三方 app，
而是自己出 app + 自己出 bot。代价由用户接受，我也就不再去找 DimRemote 的复用点位。

**这条决定顺带把架构逼到唯一解**：一个自家的手机 app 要能连上家里的电脑，
必须有**公网可达的接入点或中继**，而这与该 app 用哪个服务实现无关。见第 6 节。

## 6. QQ bot 两种模式的实测结论（2026-09-26 核过官方文档）

[QQ 机器人官方文档](https://bot.q.qq.com/wiki/develop/api-v2/dev-prepare/interface-framework/event-emit.html)
明确给两条路，**成本差一个量级**：

| | WebSocket 长连接（推荐） | Webhook 回调 |
|---|---|---|
| 方向 | **出站**（我们连出去） | 入站（QQ 推进来） |
| 公网 IP / 域名 | **不需要** | 必须 |
| 端口 | 无 | 只能 80 / 443 / 8080 / 8443 |
| 鉴权 | OpCode 2 Identify 带 `token` + `intents` + `shard`，连上即得 session | ed25519 签名校验（`plain_token` + `event_ts` 用 seed 派生私钥） |
| 连接维护 | OpCode 10 Hello 下跳周期（文档示例 45000ms）、OpCode 1 心跳、OpCode 11 ACK、OpCode 6 Resume、OpCode 7 重连 | 平台重推 |

**结论：走 WebSocket 出站。** 理由与用户「能省就省」直接一致——它**不需要公网 IP、
不需要域名、不需要端口映射、不需要反向代理**，家里电脑直连即可。第三方实现的原话即
「通过 WebSocket 连接 QQ 平台（出站连接，无需公网 IP）」，官方文档的 WebSocket 一节
（OpCode 10 Hello → OpCode 2 Identify → 心跳）也确认了这一条路径。

**这与第 2 节的入站控制面不矛盾，反而互补**：QQ bot 这一路是**出站**（连到 QQ），
因此天然不暴露本机监听面；真正需要鉴权硬闸门的是**手机 app 那一路的入站控制面**
（`POST /command` / `POST /exec`）——它才是要接到公网的那一侧。两者都要鉴权，但威胁模型不同。

## 7. 手机 app 那一路的公网问题：用户选了自建中继，我(agent)记录不同意见

自家 app 要远程连上家里的电脑只有三种形态：

| 形态 | 成本 | 代价 |
|---|---|---|
| **A 直连（组网）** | 中：用户装一个组网客户端 | 需引导用户装额外软件，但**零服务器成本、零运维**，且凭据不出本机 |
| **B 自建中继** | 高 | 要一台服务器 + 域名 + 证书 + 运维；流量经我们的手 |
| **C 走既有云函数** | 低 | [08 号](08-chendahuang-cloudflare-research.md) 已研究过「只借思想不上云」，与 C 冲突 |

**用户 2026-09-26 选 B（自建中继）。** 我(agent)把不同意见写在这里备查，不推翻决定，
因为它带来的四件事不是「多花点钱」而是**产品性质改变**，事后才知道就晚了：

1. **我们从此持有凭据。** 中继要验证「这台电脑是可信的」，就必须在中继侧存一份设备凭据或
   会话凭证。这直接撞 [ADR 0009](../adr/0009-credential-boundary-borrow-dont-hold.md) 的
   「不持有非本机既有登录态的密钥」。**ADR 0009 需要在 B 立项时一并修订**，
   不能一边写着「不持有」一边在中继数据库里存 token。
2. **我们从此看到流量。** 中继是全通路的必经点，`POST /exec` 的命令与输出都过我们的服务器。
   「不当 agent 前端」这条界还守得住，但「不转发流量」这条界守不住了。
3. **我们从此有后端要运维。** 证书续期、宕机、扩容、日志留存。今天这个仓是**单人开发、
   无 CI**（18 号 §5 表已记），中继会把「发版」从「打个 zip」变成「要管在线服务」。
   [08 号](08-chendahuang-cloudflare-research.md) 那条「不要自己写轮子，指的是守护进程/连接池」
   正是这个场景：中继就是一个要长期活着的守护服务。
4. **隐私叙事要跟着改。** 今天能对外说「数据不出你本机」；有中继后这句话不成立了，
   必须换成「流量经中继但中继不持久化命令内容」——**能说这句话的前提是中继真的不落盘**，
   否则是撒谎。这一点比技术更难守。

**如果后面想退回 A，代价只是引导用户多装一个客户端**；从 B 退回 A 则要把中继下线、
迁移存量用户。所以我把顺序建议写成：**B 做，但按「中继只是转发、绝不落盘、凭据只做设备绑定」
的最小形态先上**，并且把 ADR 0009 的修订与中继立项绑在一起，不许中继先上线、口径后补。

## 8. `POST /exec` 的权限模型（用户 2026-09-26 拍板）

**裁决：白名单默认 + 显式解锁后可任意。**

| 档 | 能做什么 | 怎么进这一档 |
|---|---|---|
| **默认档** | 只有预定义管理动作：切档位、重启 agent、发送通知、跑白名单命令（如 `git status`、跑测试） | 配对后即在此档 |
| **解锁档** | 任意 shell | **必须在电脑侧当面确认**（不是手机上点两下），且有超时自动回锁 |

**为什么不是纯白名单**：用户要「也能写代码」，而写代码天然要跑任意命令（换个分支、
装个依赖、跑个脚本）。纯白名单会把这条需求做废。

**为什么不是全程任意**：手机丢了就等于 shell 丢了。所以任意权必须满足三条：
① **解锁动作只能在电脑上做**（手机侧自己给自己解锁等于没锁）；
② **有超时**，到点自动回默认档；
③ **解锁与任意命令都进审计日志**，且日志里命令原文不落中继（第 7 节第 4 条的延伸）。

## 9. 「移动端 app 是不是一定要服务器中转」——不是二元，是四种形态

用户问：「如果要用类似 ZCode 或 DimRemote 这种的移动端 app，是不是要用服务器中转？」

**答案：跨出局域网的手机 app 只有两条腿——「让家里电脑变得可达」或「有个公网的人替你们传话」。
中转是后者，不是唯一解。** 四种形态：

| 形态 | 怎么做 | 要服务器吗 | 谁出服务器 | 核心代价 |
|---|---|---|---|---|
| **① 端口映射** | 路由器把电脑端口映射出去，手机直连 `http://你家公网IP:端口` | 不要 | 无 | 要改路由器、要面对公网 IP 变动，且电脑直接暴露在公网 |
| **② 组网（VPN 组网）** | 两端都装组网客户端（Tailscale/ZeroTier 一类），各拿一个虚拟 IP | **不要**（公共协调节点不碰你的数据） | 第三方 | 用户要装额外软件；**数据点对点不过第三方** |
| **③ 自建中继** | 自己搞服务器，两端都连它，它负责转 | **要** | **你自己** | 有后端要运维 + 我们持有凭据（第 7 节四条） |
| **④ 公网协调 + 打洞直连** | 公网服务器只帮两端「认识」，认识后两边直连 | 要（但只经手握手，不经手数据） | 第三方或自己 | 打洞成功率受 NAT 类型影响，失败要退回中继 |

**所以「一定要中转」是错的，但「一定要有公网侧参与」基本是对的**——两端大多在 NAT 后面，
总得有个人先帮它们认识。区别只在那个人**看不看得见你的数据**：

- **②④：看不见**（④只见握手，②连握手都不经我们）
- **③：看得见**（流量全过我们的手）
- **①：没有第三方，但代价是电脑直接裸露在公网**

### DimRemote 的形态：一手证据（本机实测）

你(用户)现在正用 DimRemote 跟我对话，所以它是最好的样本。本机实测：

- 二进制 `/Applications/DimAgent.app/Contents/Resources/runtime/cli/DimRemote`
  内含 `upgradeToTunnel`、`ERR_PROXY_TUNNEL`、`Sec-WebSocket-Key/Accept`、`sec-websocket-protocol`
- 进程在跑（`pgrep -f DimRemote` 可取到 pid）
- **本地监听 TCP：无**（`lsof -iTCP -sTCP:LISTEN` 无命中）

**结论：DimRemote 是「电脑主动出站长连接 + 服务端中转」**，不是等手机连进来。
证据链：它做了 WebSocket 升级与隧道升级，却**不监听任何本地端口**——
说明它不是「开服务等连」，而是「连出去找隧道」。

这解释了两件事：

1. **为什么你在外面也能用**：电脑主动连出去，穿 NAT 的是出站连接，不需要端口映射。
2. **为什么它要订阅**：中转的服务器与带宽是持续成本，订阅是收费方式。
   **你要自己做，这部分成本就得你自己背**——这是「不用 DimRemote」的真实代价，
   不是「写个 app」那么轻。

**对我们意味着什么**：你选的 ③（自建中继）与 DimRemote 同构，方向没错。
但它是**长期运营成本**，不是一次性开发成本——服务器 + 域名 + 证书 + 带宽 + 续期 + 宕机，
且必须长期活着，否则手机就失联。今天这个仓单人开发、无 CI，这是要一并接受的现实（第 7 节）。

### 我(agent)的建议：先做 ② 的形态，再决定要不要 ③

理由不是省钱，是**顺序风险**：

- ② 几乎是纯客户端工作（装个客户端 + 两端各拿虚拟 IP），**不引入我们要运维的东西**，
  今天就能验证「手机能不能操作电脑」这条核心链路。
- ③ 要等域名、服务器、证书、运维流程齐备，**链路验证被基建阻塞**。
- 链路跑通后再迁 ③，代价只是把「直连」换成「连中继」——**控制面不变**
  （第 2 节那层带鉴权的入站面与通道适配器都不用改）。

真要做 ③ 时也可以只把「打不通洞时的兜底路径」做成中继，平时仍走 ②——
这就是形态 ④ 的退路设计，DimRemote 一类产品通常也是这么分层的。
