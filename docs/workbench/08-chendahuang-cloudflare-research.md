## 原文（全文照录，未改写）

> 做独立产品最头疼的一件事，就是后端架构怎么选。
>
> 平时没几个人用，租云服务器总觉得浪费；好不容易哪天在社区火了一把，又怕突发流量直接把单机打崩溃。
>
> 我的建议是：
>
> 能利用 Cloudflare 的基础设施，就尽量全部交给它。大部分需求在这一套体系里已经足够搞定了。
>
> 常规 API 请求交给 Workers，冷启动极低，全球毫秒级就近响应。
>
> 遇到高算力或长耗时计算，直接接入 Containers 跑后台任务，完全不需要自己在机器上折腾复杂的守护进程。
>
> 如果有复杂的重型数据库需求，用 Hyperdrive 连上自己机器里的 PostgreSQL 实例，全球就近复用连接池，既保住了成熟数据库的能力，又省掉了自建连接代理的麻烦。
>
> 整套体系不仅能把固定成本压到接近 0 元，最关键的是永远打不爆。
>
> 自己租小机器看似便宜，流量一来容易遇到内存打满直接宕机；而在边缘网络跑，天然自带弹性伸缩和防攻击，就算瞬时涌进上万个并发，系统依然能稳稳接住。
>
> 大家做独立产品，后端的基石选型一般怎么定？

## 它主张的技术方案

| 层次 | 推文的主张 | 解决的问题 |
| :--- | :--- | :--- |
| 常规 API | Cloudflare Workers | 冷启动极低、全球毫秒级就近；固定成本≈0 |
| 重算力 / 长任务 | Cloudflare Containers 跑后台任务 | 不用自己写守护进程、不用管机器 |
| 重数据库 | Hyperdrive 连**自有机器的** PostgreSQL，全球就近复用连接池 | 保留成熟数据库能力，省掉自建连接代理 |
| 底座 | 边缘网络整体托管 | 弹性伸缩 + 自带防攻击，「永远打不爆」 |

核心论点是一条：**把峰值风险从「自己运维」换成「平台弹性」**，代价是固定成本降到接近 0。

## 与 AgentIsland 工作台的对照

AgentIsland 是**本机**软件（桌面端 + 本机文件/进程），跑在本机上、数据不出本机，
所以这条推文主张的「全部外包给边缘云」**不能照搬**。可对照的是三点：

1. **把「平时没人用、偶尔爆量」当成同一类容量问题**。AgentIsland 的容量曲线也是
   脉冲型：监控在跑时 1s tick、空闲时几乎 0。推文用平台弹性接脉冲，我们用
   `pollIntervalMs` 分档 + 只在实际订阅时启动轮询（见 `03-approach.md` 的性能预算）。
2. **「不要自己写轮子」在这条推文里指的是守护进程/连接池**。我们这边的等价物是
   `tokio::select!` + `JoinSet` 的任务生命周期管理，以及**不引入自己的桥接逻辑**——
   只当 DBus / hooks / LocalEventServer 的中继者，下游路径零改造。这与推文
   「不用在机器上折腾复杂的守护进程」是同一条经验的两个方向。
3. **「固定成本压到接近 0」要换算成我们的口径**：我们的固定成本不是钱，是内存与
   CPU。侧边栏常驻不能变成第二个 Electron 巨物；这一点推文不覆盖，仍按
   `02-goals.md` 的低资源目标执行。

## 可以借的思想（一句话版）

> 把偶发峰值交给一个有弹性的底座，自己的代码只写业务本身。

## 明确不适用 / 未采用

- **不上 Cloudflare**：产品是本机的，无服务端，也没有「防攻击」这个威胁面。
- **不引入自托管数据库/连接池**：todostore 就是本机 JSON/文件，重数据库是伪需求。
- **不引入后台常驻容器**：桌面上常驻的是 UI 进程本身，没有「后台任务层」可拆。
