# 后台内存优化：测量与实施方案

状态：已实施第一批优化；现有 macOS VM 的同系统 build、虚拟化、公钥通路与已登录 Aqua 均已核实，完整 UI/Dock/单实例门禁已通过，见 [隔离验收](implementation/14-native-vm-acceptance.md)。长时内存尚未通过，既有短时样本不代表 30 分钟或 20 次循环完成。

产品约束：常驻态是贴边小控件 + 托盘、Agent 监控、IM 远程通知、Token 计量。工作台可逐渐扩展为重型应用，但只能在用户主动打开时承担其资源成本。Tauri 不是必须保留的前提：优化无法达标时，可拆分进程并替换 UI 技术方案。不能通过暂停必要监控或丢弃计数实现低内存。

## 1. 实测基线与边界

2026-10-02，正式应用默认启动、未手动打开工作台，v0.0.287 主进程：

| 指标 | 单次实测 | 解释 |
| --- | ---: | --- |
| 主进程 RSS | 约 585 MiB | 驻留页，不能与所有子进程直接相加当独占内存 |
| 主进程 physical footprint | 521.8 MiB | vmmap 报告的物理占用；peak 570.0 MiB |
| Malloc Large (empty) | 驻留 250.3 MiB，交换 213.8 MiB | 有大量已经空闲的大块分配区域；不能把它们当仍存活的 Token 对象 |
| malloc zone bytes allocated | 15.9 MiB | zone 表的活跃分配，不代表进程所有框架/映射/图形内存 |

同一启动时间附近有三个 WebContent，RSS 约 32/61/57 MiB，GPU 约 39 MiB、Networking 约 4 MiB。它们由 launchd 托管，不能靠父 PID 精确归属；这是候选关联，不作为已确认独占进程合计。没有关闭其他应用验证归属。

同一未重启进程的后续样本出现 RSS 约 291 MiB、随后 footprint 395.4 MiB；采样期间有构建活动，不能据此认定优化收益或稳定下降。占用会波动，需要统一时点与系统负载。

工具：`ps -axo pid,ppid,rss,comm`、`vmmap -summary <应用PID>`。只输出指标；完整本机进程与映射摘要留在忽略目录。单次样本没有证明泄漏或长期稳定趋势。

## 2. 确认的非必要工作与待验证模块

- **隐藏窗口已创建**：tauri.conf.json 同时声明 island/sidebar/workbench。visible=false 仅隐藏，未延迟创建。启动只需要当前常驻形态；未打开工作台时不需要工作台 WebView。
- **关闭只是隐藏**：conceal_workbench_window 和 CloseRequested 保留工作台实例；没有空闲销毁策略。
- **隐藏页面继续更新**：workbench 的 engine://tick 回调始终保存快照并 renderWorkbenchMonitorOnly；后台侧边栏也订阅更新。engine_loop 向应用广播快照。
- **数据缓存缺少全局字节预算**：Token 明细是每文件 20,000 条、70 天窗口，状态表触及 8,000 个文件后删一批。单文件上限不是全局内存上限；峰值 collected/unique/fold 临时集合也需要量化。不能直接丢历史，ADR 0007 要求累计保和。
- **分配高水位待定位**：大块 empty malloc 是实测信号，但不能直接归因 WebView 或 Token。JSONL 按行读，不过完整 Value 仍会物化正文；DSH 投影使用 read_to_string。需追踪一次启动/扫描/分析请求分别引起的分配。
- **不值得优先做**：缩小图标、微调 CSS、替换几个字符串不会解释数百 MiB；也不应先换整套桌面框架或强制清空正确的累计数据。

## 3. 分阶段策略

| 阶段 | 具体动作 | 风险与验收 |
| --- | --- | --- |
| P0 基线与归因 | 记录启动 30s、5min、30min；首次打开、隐藏、再次打开；分主进程 footprint/候选 WebKit/CPU；给 Token 索引记录文件数、明细数、去重键数、容量与扫描峰值，不记录正文 | 没有归因前不承诺具体省多少；区分存活对象、allocator 保留页、压缩/交换 |
| P1 按需窗口 | 默认只创建当前 island 或 sidebar；工作台首次点击托盘/深链/快捷入口才创建；多次同时请求只创建一个 | 保留 macOS 材质、Dock 显隐、单实例；导航先入队，新窗口拿最新快照后首绘，不能等下一次 tick 才显示 |
| P2 隐藏页面暂停 | 隐藏后暂停 DOM 刷新、报表请求与页面定时任务；事件只保留一个最新快照，恢复时一次补齐；发动机监控和通知继续运行 | 分开 UI 渲染生命周期与监控生命周期，不因工作台隐藏漏掉等待确认/完成通知 |
| P3 工作台回收 | 明确关闭可销毁；普通隐藏保留短暂宽限期，候选 60–120s 后销毁；保存页面/窗口位置/滚动位置 | 先处理未保存表单和待办草稿；不能把密码、Webhook 或通知凭据序列化到文件；支持用户选择保持工作台常驻 |
| P4 主进程数据预算 | 先追踪大块分配来源；对读取器使用选择性反序列化/流式提取，避免物化正文；复用小缓冲，裁掉巨型缓冲容量；Token 索引采用全局字节预算、LRU、历史按模型/时间折入 | 超预算不得静默少算或跳过长行；冷扫描与增量计数必须一致，累计、24h、图表和通知阈值回归必须通过 |
| P5 后台调度 | 精简重复 clone/序列化；UI 只向可见窗口发布，隐藏窗口只留最新值；未打开分析页时不预构建明细图表；空闲扫描降低频率、文件戳变更触发更新 | 托盘/贴条状态仍及时；新鲜 Token 增长、阈值和远程通知不能被降频破坏 |

先做 P0+P1+P2；因为它们既可测又有明确闲置工作证据。P4 的分配追踪同步推进：主进程 522 MiB 说明单靠关掉一个 WebView 未必足够。是否实施 P3 的销毁时机，在验证草稿恢复后定案。

## 4. 目标与验收

候选预算：后台仅贴条+托盘时，已确认归属的整体 footprint 目标约 100 MiB，暂定 150 MiB 为进入架构替换评估的上界。Rust 服务目标 30–50 MiB，其余预算给常驻控件和平台运行时。不能把 UI 子进程排除后宣称达标；共享页用进程组工具复核，避免重复计数。这是待基线验证的工程目标，不是当前实现承诺。工作台冷打开目标 1s 内首绘，热恢复 300ms 内；需在真实机器记录 p95。

- 连续空闲 30min，内存不持续线性增长；打开/关闭工作台 20 次后回到可解释的稳定范围。
- 主进程、WebKit、GPU 分开报；以 footprint 为主要内存指标，RSS/压缩/交换辅助，避免重复相加共享页。
- 未打开工作台时窗口登记表不包含 workbench；需要时一份实例，所有导航入口正确。
- UI 不更新时 CPU 接近空闲；贴条、菜单、监控、Token 计数、阈值、IM 通知仍正常。
- 数值通过相同输入的冷/热扫描对照；全局预算不得使累计缩水。
- 应用重启、Dock 显隐、单实例、三形态 UI、凭据脱敏门禁全部通过后才发版。

最终生命周期决策应进入 CONTEXT / ADR；测量数据与本阶段计划仍放本文件，不把未实施方案写成 README 功能。

## 5. 无法达标时的架构路线

先测一个不创建工作台、不创建第二常驻窗口的版本，以及单独运行 Rust 监控核心的版本；用差值判断 UI 固定成本和监控分配成本。如果核心自身过高，先治理读取/缓存/allocator 高水位；替换 UI 不会自动修复核心分配。如果 UI 固定成本占主要预算，进入下一路线，不无限微调 CSS 或开关掩饰。

```text
轻量常驻服务（Rust）
  ├─ Agent 状态 / Token 账本与阈值 / IM 通知 / 钥匙串
  ├─ 托盘 + 一个轻量原生贴边控件
  └─ 用户主动打开 → 独立工作台进程
                       ├─ 工作区 / 报表 / 配置 / 后续重型功能
                       └─ 明确关闭 → 退出进程并归还工作台资源
```

- 工作台通过本机 IPC 获取小快照与按需明细；不复制完整会话库，不重跑第二套监控，不接管通知队列。凭据留在服务与钥匙串，不传递给前端持久化。
- 可先保留现有 Web 工作台代码作为独立 UI 进程；常驻贴边控件若 WKWebView 固定成本仍过高，改为原生平台控件。Rust 跨平台核心和共享协议保留，平台 UI 用适配层实现，不恢复归档 SwiftUI 端。
- 工作台崩溃、更新或退出不得中断通知和计量；服务与 UI 分别测量启动/稳定/销毁曲线。
- 全部替换是最后一个工程选项，不先假定新框架更省内存。候选方案须用真实贴边交互与相同监控输入做小原型，比较内存、空闲 CPU、冷启动、平台一致性和维护成本，再定案。
- 一轮有边界的窗口/后台优化若仍不能接近预算，立即评估进程拆分/原生常驻 UI；不以“现在用的是 Tauri”作为继续接受数百 MiB 的理由。

## 6. 第一批实施与测量结果（2026-10-02）

- 三个窗口均声明 `create=false`，启动仅创建当前常驻形态；工作台按需创建，深链先排队，销毁后重新建立订阅。
- 引擎仅向可见窗口发送快照；隐藏页面暂停 DOM 刷新和布局定时器。监控、Token 和通知引擎继续执行。
- 工作台隐藏后由 Rust 计时 90 秒；无草稿且仍隐藏时销毁，重新显示使旧回收计时失效。使用原生计时是因为隐藏 WebView 的 JavaScript 定时器可能暂停。只恢复页面选择，不持久化表单凭据。
- macOS Rust 分配改用 mimalloc，采样完成并释放引擎锁后收集闲置页；AppKit/WebKit 的分配器不变。系统分配器的空闲大块保留是已测到的主要增长来源；本轮没有缩减 Token 历史或停用通知。

以下为同机短时诊断样本，不能代替长期验收：

| 样本 | physical footprint | 边界 |
| --- | ---: | --- |
| v0.0.288 默认主进程，8–32 秒 | 135 → 306 MiB | 原分配器、正常窗口启动 |
| 无 UI 的 Rust 核心，原分配器，8–32 秒 | 110 → 453 MiB | 保持实际监测输入 |
| 无 UI 的 Rust 核心，mimalloc + 闲置收集，16–32 秒 | 33.0–33.6 MiB | 核心占用，不是整个应用 |
| 隐藏测试实例，仅一个常驻 WebView | 主进程约 52 MiB；资源 coalition 合计约 89 MiB | 短时隐藏测试，不能宣称可见 UI 已达标 |
| 已创建工作台但尚未回收的隐藏测试实例 | 合计约 153 MiB | 旧 JavaScript 回收计时未执行，促成原生计时修正 |

Rust 回归 592 项通过，6 项忽略；窗口 lease 测试覆盖草稿保护与重新打开取消回收。原生测试曾发现深链回调内创建窗口的锁重入，现已延后至主线程队列；诊断 HTTP 失败也已捕获。最新修正尚未再次启动原生 UI 验收。

**验收限制**：30 分钟稳定性、20 次打开关闭、原生回收后的整体占用、可见窗口首绘 p95 尚未验证。不能把核心 34 MiB 表述成整应用内存，也不能以隐藏测试样本宣称全部预算达标。原生应用即使隐藏启动也可能抢焦点，因此 UI/Dock 脚本要求显式 `--isolated-session`，仅在隔离用户会话或虚拟机运行；本轮不自动启动或重启应用。

## 7. 会话候选临时分配

filemon::probe_files 原先把缓存内所有路径克隆、排序，再去重取16。现改为借用元数据的有界批次合并：保留16条上一批结果，加256条候选，最多272个借用引用；局部排序去重再保留16，只有最终路径克隆。缓存本身、扫描TTL、完整活跃会话计数和解析器最多16条探测行为不变。

固定10万条合成记录、每路径143字节：旧算法克隆路径正文至少14,300,000字节，最终输出同样16条、2,288字节。新算法临时引用/去重表另占常量空间；这不是整个进程RSS下降值，不测量缓存本身或WebKit。差分回归覆盖重根/重复路径、不同mtime、同时间词序、反转/旋转输入、批次边界、空集合及目录缓存共用。

同源码辅助函数以 rustc -O 单独编译，5次固定合成对照（三种输入顺序每次都断言输出一致），耗时中位数：混合8.62→1.38 ms、最旧优先3.71→1.63 ms、最新优先6.84→0.58 ms。该选择步骤不含目录枚举、会话解析、Token索引、通知或UI。开发模式混合/最旧优先更慢，不能用其计时推导生产表现；优化编译测量也不能抵扣30分钟稳定性、原生整体footprint或交互验收。

## 8. 核心阶段诊断

显式无界面诊断 `dist/agentisland --memory-core-probe --probe-samples 3 --probe-interval-ms 2000` 输出有版本的JSON行：样本序号/时间、进程采样、安装探测、文件元数据/候选、会话解析、Token读取、缓存计数检查及其他引擎工作的微秒耗时。total_us 包括诊断计时和cache_stats_us，不含等待、JSON序列化或闲置页收集；reclaim_us 单独记录。数字缓存字段是条目/容量，不是字节、footprint或账单。File缓存记录根数、文件数和容量；Token缓存记录文件状态、明细条目/容量、去重键/容量，不含路径、模型、会话正文、凭据或通知内容。

默认仍20次/2秒；样本1–900、间隔100–60000ms，在读取设置/建引擎前校验，不重复参数、不自动无限运行。`--process-only` 仅测进程刷新；`--without-usage` 明示Token刷新关闭，用于归因对照；`--retain-allocator-pages` 禁用闲置页收集用于诊断。禁止把关闭用量的样本当真实常驻资源预算。

观察引擎硬性跳过外发调度与钥匙串入口，仍保留本地事件和计量状态；不创建窗口/钩子，不写配置。正常应用不启用这些计时或统计，不自动静默用户通知。数据只保留最近一拍的元数据，历史由调用方按需保存在忽略目录。诊断读取的是实际本机状态，仍需区分冷/热、系统负载与同输入；核心诊断不能验证WebKit、原生动画、窗口回收或整个应用footprint。

三次本机核心诊断（普通应用同时运行、未控制全部工作负载）总耗时946.55/418.29/378.55ms；文件元数据505.26/374.87/336.95ms，Token405.15/0.02/0.01ms，会话25.49/34.02/33.87ms。缓存保持19根/5316条元数据、147个Token文件状态/8577个明细及去重键。说明该短时样本的热阶段主要耗在文件元数据，不能推导全应用耗电/footprint或直接放宽扫描时效。非法参数、process-only单样本及without-usage显式对照已用新CLI验证；stdout只有JSON元数据、stderr空。完整长期基线仍待隔离原生环境。

## 9. 完整时间戳与有界路径驻留

核对元数据扫描发现旧代码在每根4,000个文件处静默停止；该限制可能遗漏后续最新会话与活跃计数，不能视为有效资源预算。扫描沿用深度、跳过目录、扩展名、2秒TTL和链接策略，取消静默条数截断；缓存对所有可读取信号文件保留mtime，按时间戳计算活跃数量，候选路径以有界批次流式选择，每根只驻留最近16条唯一路径。跨根全局候选排序/去重仍由原算法决定，不扩展解析器最多16条候选限制。

mtime向量仍随可读取文件数量增长，属于需要继续测量的完整元数据成本，不宣称整个索引有固定字节预算；路径临时工作集最多272条，已知前沿之前的较旧文件只记录mtime、不分配路径正文。无法读取的条目仍沿用原行为，这一变化不宣称解决所有可观测性错误。

诊断file_cache.files/file_capacity现在统计完整mtime条目/容量，cached_candidates单列驻留候选数；不能把候选数当总文件数。4,101文件回归核实活跃总数、旧截断位置后的最新文件、16条候选与缓存口径；空/同时间/重复路径、多mtime与批次边界匹配完整排序。修正后本机源文件计数可能增加，不能拿旧截断数据与新完整数据直接宣称速度收益。

完整扫描构建后的无UI诊断：3样本/2秒，stderr空。19根、5316条时间戳、158条缓存候选；时间戳容量6892。总耗时723.28/381.36/394.42ms，文件阶段322.65/338.98/352.94ms。正常应用同时运行，未控制工作负载，仅为阶段归因样本；不能据此宣称整应用内存或UI响应预算达标。


## 10. 只读既有应用资源采样

`python3 scripts/measure-memory.py --pid <现存应用PID> --seconds 30 --interval 10` 使用public libproc `proc_pid_rusage` v2读取驻留/footprint和累积计数，不启动、关闭、显示或移动窗口，不调用vmmap暂停式摘要。参数有界；目标启动身份变化或不可读以结构化状态退出2，过期采样槽跳过而不补发。输出schema2，仅闭合角色、PID和数值，无参数/路径/会话正文。CPU时间保留raw字段，未按未验证单位算百分比。

coalition检查仍使用XNU私有proc_pidinfo flavor20，不能保证未来版本支持。采样器与目标共组或任一组不可核实则降为main-only，不把Codex父组计入应用。枚举和rusage身份、归属两次核对是非原子观察，缺读与无法确认归属显式记录；可读成员的已知账本合计与完整total分开，缺数据/不稳定时total为null。complete仅指本次枚举可核实范围，不是系统独占内存或未来成员覆盖证明；不把成员RSS相加。
