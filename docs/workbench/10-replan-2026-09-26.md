### 阻塞三 · 扫描器对真实 key 零命中，而 Phase 2 就要碰真 key

`scripts/scan-secrets.sh` 的 8 条规则全是 `grep -InE` 纯模式匹配。我(agent)用假值在 `/tmp` 独立复验过（未写入仓库）：

| 形态 | `cred_prefix` | `secret_assign` |
| :--- | :--- | :--- |
| `sk-` + 16 位 base62 | ✅ 命中 | ✗ |
| `sk-proj-…`（OpenAI 实际前缀） | ✗ **漏** | ✗ |
| `sk-ant-api03-…`（Anthropic 实际前缀） | ✗ **漏** | ✗ |
| `AKIA…`（AWS） | ✅ 命中 | ✗ |
| `apiKey = "…"`（camelCase） | ✗ | ✗ **漏** |

三个结构性缺口（均在 `risk-and-acceptance.md` A1）：

1. **只看内容不看数据流**：`payload: serde_json::Value` 里的 key 脱敏后仍是任意长随机串，规则零感知。
2. **`grep -I` 跳过二进制**（实测含 NUL 文本零命中），`dist/*.zip` 被 `.gitignore` 排除——本机 `dist/` 里已有一批发布 zip，闸门**一次都没扫过**。
3. `secret_assign` 要求值带引号，`.env` 风格与 Rust `format!` 插值不带引号。

**一个反向事实要说清**：正因为规则窄，万一真 key 长得标准，命中的是 `cred_prefix`——这一条是**绝对零命中、不许进 baseline**（`scripts/scan-secrets.sh:56-57`），`release.sh` 是 `set -euo pipefail` → **发版直接断**。所以最坏情况是「发版时炸」而不是「发出去后道歉」，这是好事，但不该当成设计。

**对策**（按优先级，详见 `risk-and-acceptance.md` A1）：掩码做成**类型**而不是函数（`ProviderSecret(String)` + crate-private `init` + 手写 `impl Serialize`），让「忘加掩码」变成编译不过；`log_line` 与 `log_from_ui` 统一出口并脱敏；产物（`dist/*.zip`）进扫描范围。扩规则这条**降级为可选**——它会立即产生新增命中，要 `--rebaseline` 备案，且不解决「数据流」这个根本缺口。

## 4. 修正后的技术方案

### 4.1 双形态的真相修正

原方案（[03-approach.md](./03-approach.md) §2）说「island 分支零改动，只分派 `placement.rs`」。核实后要改三处：

1. **CSS 隔离今天正好是反例**：`index.html:11` 只有一个 `<div id="root" class="edge-top">`，`island.css:12,19-22,76` 把 `#root` 与 `.edge-*`、`--notch-inset` 写成**全局**规则。03 自己把「两壳不共根容器」列为硬要求，代码今天是它的反例 → 这是 Phase 1 的**第一件事**，不是最后一件。
2. **窗口高度写死钳 520**：`main.js:59` 与 `:117` 都是 `Math.min(..., 520)`。侧边栏必须放开，放开后 `resizeToContent`（阈值 `|Δ| > 6`）每次 tick 都可能触发 IPC + resize → 改为「只在用户手动改宽/首次展开时 invoke」。
3. **Tauri 端失焦收起是明确放弃的**（`main.js:168-170` 注释），侧边栏 `focus: true` 且接键盘，**不能沿用「光标离开就收起」**。侧栏失焦策略单独定义：失焦不收起，只有主动 ⌘W / 切形态隐藏。**与灵动岛显式区分，不要试图统一。**

### 4.2 `provider.rs` 两层模型

```rust
pub struct ProviderProfile {
    pub id: String,
    pub tool: Tool,                 // Claude | Codex
    pub name: String,
    pub payload: serde_json::Value, // provider 专属：model + base_url + 凭据
    pub shared:  serde_json::Value, // 该工具的通用片段：插件/hook/非凭据环境变量
    pub source_path: PathBuf,
    pub created_at: i64,
}

// 写 live 前组装；切走前重新提取，把用户在工具里新装的插件自动带到下一个档位
effective = deep_merge(shared, payload)
on_switch_away: shared = extract(live) − payload 专属键 − 凭据键
```

**凭据过滤范式直接抄 CC Switch**（`provider/mod.rs:6349-6402` 的注释原话）：「故意从严——多剥一个非机密键只是它不被共享（可恢复的小不便），漏剥一个凭据则会把密钥注入到每个供应商（不可恢复的泄漏）。用模式匹配覆盖整类，而非枚举具体名字」。实现为 `is_sensitive_config_key()`：后缀表（`_KEY` / `_TOKEN` / `_PAT` / `_PWD` / `_PASS`）+ 精确表 + contains 表（`SECRET` / `CREDENTIAL` / `PRIVATE_KEY` / `BEARER_TOKEN`）三重匹配。它与 DTO 掩码合成同一条机械守卫：**凭据不出现在任何非 live 路径。**

写实现：

| 工具 | 合并方式 | 格式保真的边界 |
| :--- | :--- | :--- |
| Claude `settings.json` | JSON 深合并 | JSON 无注释；承诺**键序**不重排（`serde_json` 开 `preserve_order`）。CC Switch 的 Claude 侧反而 `sort_json_keys()` 重排——**不抄那一半** |
| Codex `config.toml` | `toml_edit` 文档模型 | 注释、键序、多行数组格式全保留。**禁止 parse→stringify**：CC Switch 的 C5 回归锁注释写得很直白，smol-toml 的整文档重序列化会丢注释、按字母序重排键、并为 dotted 表生成多余的空父表头 |

**为何必须**：本机 `~/.codex/config.toml` 有 11 个 `[plugins."x@marketplace"]` 复合键名 + 2 个多行数组 + 6 个 `[projects."<绝对路径>"]`。朴素序列化一冲，用户一启动 codex 发现插件全丢——立刻可察觉且不可逆。

### 4.3 按工具的生效语义（Phase 2 的可判定验收核心）

| 工具 | 改文件后已在跑的进程 | 一手证据 |
| :--- | :--- | :--- |
| Claude Code | **热生效** | 官方 env-vars 页：*"A running session applies new and changed values to its environment when you save the file"*。例外：启动时只读一次的特性（如 OTel）不改 |
| Codex | **必须重启进程** | `codex-rs` `Config` 启动时一次性构造，全仓 grep `reload`/`watch` 零命中；官方 issue #3860 描述的正是这个缺口 |

**顺带一个语义坑**：Claude 的 `env` **只能加不能删**（官方原话 "Removing a variable from the file doesn't unset it in a running session"）。所以「切回官方登录」这个档位**不能靠删 `env.ANTHROPIC_BASE_URL` 实现**，要么写空串，要么走 `apiKeyHelper`。CC Switch 的第三条路是供应商列表里永远自带一个「Official」档位，切过去后让用户自己 `/login`。

**落到界面**（这是差异化点，不是重复劳动）：
- 档位卡片按工具显示生效语义：Claude =「下一次请求即用新档」；Codex =「**需重启 Codex 进程/终端**」。
- 切换动作后给出这个提示。**不要去 kill 用户进程**——CC Switch 40k+ 行 Rust 里 grep `kill|terminate|pkill` 只命中 Windows 的 npm shim 修复，它把重启完全推给用户，我们照做，但**要明说**（它的三处文档在「Claude Code 要不要重启」上自相矛盾，issue #3057 也报这个）。
- 档位卡片显示该 agent 的当前五态与最近一次切档的生效状态（已生效 / 待重启）。**CC Switch 结构上给不出这个**（它不读会话尾、不做五态）。

### 4.4 Codex 档位用原生 profile

- 档位写成 `${CODEX_HOME}/<name>.config.toml`，用 `--profile <name>` 激活。
- provider **定义表**只写在 base `~/.codex/config.toml` 的 `[model_providers.<id>]` 里；profile 文件只做 `model_provider` 指认——`ConfigProfile` 有 `model_provider` 但**没有** `model_providers`（`profile_toml.rs`）。
- `wire_api` 只写 `"responses"`（`WireApi` 现在只有一个变体，`"chat"` 有专门拒绝错误）。
- **不要生成旧 `[profiles.*]` 写法**，会被 Codex 主动报错拒绝。
- 一条硬边界：`PROJECT_LOCAL_CONFIG_DENYLIST` 里有 `model_provider` / `model_providers` / `profiles` —— 仓库里的 `.codex/config.toml` **永远改不了 provider**，所以「项目级自动切档位」在 Codex 上做不了。

### 4.5 写盘的机械要求

| 要求 | 现状 | 对策 |
| :--- | :--- | :--- |
| 原子写 | [settings.rs:58-63](../../app/src-tauri/src/settings.rs#L58) 的 `save()` 是裸 `fs::write`，无临时文件 + rename | `provider.rs` 不能照抄。临时文件 + `rename` |
| 备份 | `grep -rn '\.bak\|backup' app/src-tauri/src/` 命中的全是**损坏降级**语义，不是用户可触发还原 | 从零建：`<name>.bak` + `<name>.bak.meta`（原路径/大小/sha256/时间/是否含凭据），切换前把原 sha256 记进 meta，还原前校验，不一致拒绝 |
| `auth.json` | 含 `refresh_token` + `last_refresh` | **默认不动**。只读用于展示「本机已登录」。若一定要动，还原连 `last_refresh` 一并还原并提示「还原后可能需重新登录」 |
| 写后自校验 | 无 | 用同一套解析器重读刚写的文件，读不出就**立刻从 `.bak` 还原**并返回错误 |
| `.bak` 的 git 状态 | `.gitignore:51-59` 有 `*credentials*` / `*secrets*` / `.env*`，但 `.bak` 不匹配任何一条 | **必须显式加**（如 `*.agentisland.bak`） |

**从 CC Switch 抄的三条最有价值的工程经验**（不是「切换」这个动作，是它处理失败的方式）：
1. **预检在提交之前**（`live.rs:728-748` 的注释：写层在 current 移动之后拒掉，会让下一次切换把旧 live 回填进新 provider）。
2. **回滚是显式的文件快照**（`capture()` 拍 4 个文件，任一失败整组还原）。
3. **失败降级为 warning 且要说清为什么不再升级为错误**。

### 4.6 数据存储位置（与项目凭据口径冲突，需拍板）

CC Switch 全明文 SQLite + JSON 放 `~/.cc-switch/`，**不用钥匙串**。我们的口径是「凭据只进钥匙串、UserDefaults 零密钥」（`CONTEXT.md`）。**只能融合它的机制，不能融合它的存储策略。** 具体见第 8 节问题 3。

### 7.0 追加的范围收窄（用户明确）：**Phase 2 只做 Codex 一家，不做 Claude Code**

理由（用户原话「我用 codex 但我不用 claude」）+ 本机实况双重支持：

- Claude Code 本机 `~/.claude/settings.json` 顶层只有 `permissions` 与 `hooks`，**没有 `env` 块**——
  即没有 API key / base_url / model 的落点。在一个没有 env 块的机器上，「切 Provider」没有可切的东西。
- 只做一家反而让 Phase 2 更干净：`provider.rs` 不必处理「两家配置格式不同 + 生效语义不同」的组合，
  只需吃透 Codex 一套（`$CODEX_HOME/<name>.config.toml` + `--profile`）。

**随之改写的能力边界**（原写「只做 Claude Code 与 Codex 两家」）：

1. Phase 2 的产品名建议从「Provider 切换」改为「**Codex 配置档位**」，不要用会暗示支持多家的词。
2. 「不做另外 N 家」的口径随之消失——本来就只有一家要做。README/界面不要出现「暂只支持 2 家」这类表述。
3. 用户可见界面必须写清两件事：① 此档需 `codex --profile <name>` 启动（问题 4）；
   ② Codex 的 `Config` 启动时一次性构造，**切档对已在跑的进程无效**（问题 6 + issue #3860）。

## 7A. 原始问题与推荐答案（保留作为决策记录）

以下是拍板前的提问原文，保留是为了让「为什么这么定」可回溯。**已定项以 §7 表格为准。**

### 问题A1 · `app/` 构建阻塞怎么解（**最优先，其余都依赖它**）

本机无 Rust 工具链，`cargo tauri build` 从未成功过，而整个 Phase 1/2/3 都以 `app/` 为地基。

- **A. 先在本机装 Rust 工具链并让 `app/` 构建成功，再进 Phase 1**（推荐）
- B. 把 Phase 1 改成在 `Sources/` 上加侧边栏（SwiftUI），放弃 Tauri 端
- C. 暂停整个改造，先处理别的

**推荐 A 的理由**：`app/` 的 2,670 行 Rust + 690 行前端是双形态与跨平台唯一的地基，而 `Sources/` 侧加侧边栏要重做 CSS 隔离、窗口定位、键盘可达三件事，且与「跨平台工作台」的定位相反。但 A 的前提是装工具链这件事本身需要用户点头——它会影响本机环境。

### 问题A2 · Phase 0 是否值得单独发一版

Phase 0 的新增内容（Rust 测试基建 + `app/` 能构建 + 测试脚本入库 + `dist/` 扫描）**不是用户可见功能**。

- **A. 不发版，作为内部地基直接推进，Phase 1 完成后再一起发**（推荐）
- B. 单独发一个版本（Phase 0 是可验证的地基，先落地先受益）
- C. 只做「测试脚本入库」这一条（最小、立刻可做），其余并入 Phase 1

**推荐 A 的理由**：Phase 0 的四件事里三件没有用户可见面，单独发版会让 CHANGELOG 里出现一个只有工程内容、没有功能变化的版本。C 是个合理的降级——如果你希望尽快把「文档引用一个不存在的文件」这个洞堵上，可以先只做那一条。

### 问题A3 · provider 档存哪（与项目凭据口径冲突）

项目口径是「凭据只进钥匙串、UserDefaults 零密钥」。CC Switch 的做法是全明文 SQLite + JSON。

- **A. 档位元数据放 `data_dir/agentisland/providers.json`，凭据字段**单独**进钥匙串**（推荐）
- B. 全部明文 JSON（像 CC Switch），但文件设 0600 且进 `.gitignore`
- C. 全部进钥匙串

**推荐 A 的理由**：B 直接违反 `CONTEXT.md` 的凭据口径，且一个明文文件里放 20 个 API key 的风险面太大；C 会让钥匙串里堆满条目且备份/迁移困难。A 的代价是要自己做「凭据与元数据分离」的存取层，且 `.bak` 备份文件仍含完整 key——这一点无法回避（备份的意义就是保留原字节），只能靠 `*.agentisland.bak` 的 gitignore + 0600 权限 + 不进 DTO 来兜。**注意这条会推翻 CC Switch 的可抄性的一半。**

### 问题A4 · 本机实况（先于原问题 4 读）

2026-09-26 在本机实测，两块都装了、且实况与方案假设有出入：

| 项 | 实测 | 对方案的影响 |
| :--- | :--- | :--- |
| Codex 版本 | `codex-cli 0.155.0-alpha.16.4` | 比方案假设的 0.134+ 更新，profile-v2 确定在位 |
| `codex --help` 原文 | `-p, --profile <CONFIG_PROFILE_V2>` —— **Layer `$CODEX_HOME/<name>.config.toml` on top of the base user config** | ⚠️ **方案表述要改**：profile-v2 不是「替代 base」而是**在 base 之上叠加一层**。所以「A（profile）vs B（改 base）」不是二选一——真实语义是三层，B 一直在底层 |
| 本机 profile 现状 | 无 `~/.codex/*.config.toml`、无 `profiles/` 目录，`CODEX_HOME` 未设 | 今天一个档位都没有；Phase 2 是从零建，不是迁移 |
| `config.toml` 里的模型键 | `model` / `model_reasoning_effort` / `service_tier` 全在**顶层** | 「档位」要切的就是这几个；base 里已有值意味着 profile 层是覆盖它们 |
| Claude Code `settings.json` | 顶层键只有 `permissions` 与 `hooks`；`permissions.allow` + `hooks.UserPromptSubmit` | ⚠️ **本机没有 `env` 块**——方案里「Claude Code 的 env 热生效」这条优势，**本机尚无可用对象**。Phase 2 的 Claude 侧第一版实际只能切「权限/hooks 的增补」，不是切 key |

两条修正由此而来：

1. 原问题 4 的问法从「要不要接受用户带 `--profile` 启动」改为「**profile 层叠在 base 之上，我们要不要用这一层**」——因为用它与不用它，base 都在底层。
2. Phase 2 的 Claude 侧能力边界要重写：本机 `settings.json` 只有 `permissions` 与 `hooks`，
   没有 `env`（即没有 API key / base_url / model 的落点）。**在没有 env 块的机器上，
   「切 Provider」这个功能没有可切的东西。** 这一条要进用户可见的界面说明，不能让人以为装了就能切。

### 问题A4b · Codex 档位是否接受「用户必须带 `--profile` 启动」

用原生 profile（`${CODEX_HOME}/<name>.config.toml` + `--profile`）的代价是：用户得改启动命令。

- **A. 接受，且在界面上明写「此档位需以 `codex --profile <name>` 启动」**（推荐）
- B. 不写 profile 文件，改为直接改 base `config.toml` 的 `model_provider` 指向（立即生效但需重启，且不再是独立档位）
- C. 两条都做：默认 B，提供「高级：存为原生 profile」选项

**推荐 A 的理由**：B 的问题是我们自有的档位与 Codex 实际状态脱钩——用户手改 `config.toml` 后我们的 UI 就不知道真实状态了；而 A 让「我们的档」和「Codex 认识的档」是同一个东西，这是这个方案唯一比自造格式强的地方，放弃它不如不做。C 的代价是两套语义要在 UI 里同时说清，违反「模式名只用一代」的原则。

### 问题A5 · Phase 4 的 reduce-motion / 彩色存量是否提前

`accessibilityReduceMotion` 只覆盖 3 个 View、2 处 AppKit 动画读不到环境值、Web 端零覆盖；彩色存量 7 类令牌在用（含 `sydedockCyan` 64 处当数据色）。这些都是 `Sources/` 的债。

- **A. 维持 Phase 4，本轮只保证「侧边栏新建部分接唯一真源」**（推荐）
- B. 提前到 Phase 1 一并做（把 macOS 本体的动效全部接上唯一真源）
- C. 单独立项，作为改造后的第一个独立版本

**推荐 A 的理由**：本轮已确认「不改 `Sources/`」，B 会把这个边界打破并显著扩大改动面；C 是 A 的自然延续，只是把它从「Phase 4 的一条」升格为独立工作项。**若选 C，请在 04-plan.md 的开放项里显式记下，否则它会掉出本轮。**

### 问题A6 · 「Codex 档位需重启」要不要做成主动检测

CC Switch 完全不检测 agent 是否在跑、不提示需重启。我们如果做检测（切档前查该 agent 是否有活动会话，working 时提示），那是差异化；如果不做，就是把 CC Switch 的体验原样复制。

- **A. 做「只读检测 + 明确提示」，不 kill 进程**（推荐）
- B. 不做检测，只在界面上静态写「Codex 需重启」
- C. 做检测 + 询问是否代为重启进程

**推荐 A 的理由**：A 的成本很低（我们已经有五态状态机，`working` 这个信号是现成的），收益是档位卡片能显示「当前会话仍在使用旧档」——这正是 §4.3 说的差异化点。C 不要做：kill 用户的 agent 进程是破坏性操作，用户可能正在跑长任务，这个风险远大于收益。
