# 外发交付状态与故障升级：交付与验收（NOT-05）

对应需求 [NOT-05](需求.md)「策略、升级与交付状态」中矩阵场景的三处缺口：
**Retry-After**、**故障升级不循环**、**受理 ≠ 收到 ≠ 已读**。
矩阵其余场景（总开关不出网、静默/节流/在场、渠道独立、失败升级）此前已有，
本篇只覆盖新增部分。矩阵映射见 [需求测试矩阵](需求测试矩阵.md)。

## 产品契约

### 交付状态三段（受理 ≠ 收到 ≠ 已读）

- 外发结果落进 `DeliveryState`：`accepted` / `received` / `read` / `unknown`。
- **受理不等于送达**：本产品绝大多数渠道只能走到「平台受理」（HTTP 2xx）；
  `received`/`read` 需要对端回执，在回执能力接入前**一律不填**。
  显示为「已受理，未确认送达」——把受理显示成「已送达」是替对端做它没做过的承诺。
- 失败、被策略挡下、未配置一律 `unknown`（「未确认」），不冒充任何一段。
- `Outcome::Delivered` 已更名为 `Accepted`：名字与语义一致（原名「送达」、文案「已受理」）。

### Retry-After

- HTTP 429/503 → `Outcome::Throttled`（限流），不再当成一般失败。
- 响应头 `Retry-After` 只认**秒数**形式，毫秒级带出给界面（「约 N 秒后可重试」）。
- HTTP-date 形式**不解析**：本机墙钟可回拨，拿它算差值会给出负数或荒唐的等待时长；
  解析不了就只显示限流本身，不编一个数。
- 超过 1 小时的秒数也不当真——那是对端在说「明天再来」，不是可信的退避计划。

### 故障升级不循环

- **连续** 3 次临时失败（`Failed { permanent: false }`）→ 通道升级为「故障」。
- 升级态经 `remote_escalations` 出口到界面，**渲染为设置页里的故障告警条**
  （`[data-remote-escalated]`：指名通道、说明已停止自动重试、提示恢复一次即复位）。
- 升级后该通道自动外发**停止重试**：再试一次不会让抖动的链路变好，只会把失败风暴
  堆在用户屏幕上（「不循环」）。
- **一次成功即复位**升级；否则用户会被永久卡在「故障」里。
- **不计入升级**（两类行为，须分清）：
  - 对端明确拒绝（`permanent`，配置错）与限流（`Throttled`）：**连击清零**。
    它们不是链路抖动，继续累加会把「配置错一次 + 抖动两次」误判成通道故障。
  - 被策略挡下（`Suppressed`/`NotConfigured`）：走闸门早退、**一次都没试网络**，
    因此连击**保留不动**。
  把「配置就是错的」显示成「通道在抖」会把人引向完全错误的排查方向。
- 升级态**不吞结果**：升级后每次失败仍如实返回、如实记账。

`drain_headers_for_retry_after`。两条读头路径不能叠着用。

## 仍未验 / 局限

- **回执能力未接入**：`received`/`read` 两段在任何渠道上都没有来源，
  当前一律显示「未确认」。接入任一有回执的渠道（如 ntfy 消息 id 查询）时再补。
- SMTP 的失败分类不走 HTTP 语义：`smtp.rs` 的 `Failed` 不解析对端的限流回复码，
  429/503 语义仅覆盖 HTTP 渠道。
- 升级态只在进程内存，重启后从 0 起算（与 `notify_duplicates` 等既有计数同口径）。
- 界面告警条只在设置页的「最近外发」区刷新时出现；岛内/窄条**不显示**通道故障
  （设计取舍：那是设置问题，不是待处理提醒）。
- 未做真实渠道（ntfy.sh 等）的限流实测：`Retry-After` 的读取与文案由本地 TCP 测试证明，
  真实渠道的限流行为取决于服务商。
